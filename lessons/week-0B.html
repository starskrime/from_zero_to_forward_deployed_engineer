Core · HTTP and httpx

1. HTTP in one picture

Every API call is a request (a method like GET or POST, a URL, headers, and sometimes a body) followed by a response (a status code, headers, and a body, usually JSON). LLM APIs, CRMs and ticketing systems all work this way.

StatusMeaningWhat your code should do
200–299SuccessRead the body
400Bad request (your input is wrong)Don't retry; fix the input and report it
401 / 403Not authenticated / not allowedDon't retry; check the key or permissions
404Not foundOften a valid answer: "this doesn't exist"
429Too many requests (rate limit)Wait, then retry (respect Retry-After)
500–599Server errorRetry a few times with growing waits

2. Calling an API with httpx

    resp = client.get("https://api.zippopotam.us/us/75024")
    print(resp.status_code)                        # 200
    data = resp.json()                             # dict parsed from JSON
    print(data["places"][0]["place name"])         # Plano

The ZIP-code API returns this JSON (no key needed):

             "state": "Texas", "state abbreviation": "TX"}]}

3. Failing well: raise_for_status, timeouts, retries

resp = client.get(url)
if resp.status_code == 404:
    return None                     # a real answer: no such ZIP
resp.raise_for_status()             # raises httpx.HTTPStatusError for any other 4xx/5xx

Networks fail. Retry only what can succeed on a second try: timeouts, connection errors (httpx.TransportError) and 5xx responses. Wait longer each time (0.5s, 1s, 2s…), which is called exponential backoff. Never retry a 400: it will fail the same way.

Why this matters for agentsLLM APIs return 429 and 5xx errors under load. Every agent you build needs exactly this retry logic. In Week 6 you'll also design tools that report errors this clearly back to the model.
Production reality
  • A 200 is not proof of success. Maintenance pages and proxies sometimes answer 200 with an HTML body. resp.json() then raises json.JSONDecodeError, a ValueError that except httpx.HTTPError doesn't catch, and an empty "places" list raises IndexError. Put the parsing inside your error handling too, and turn any failure for one record into a warning for that record.
  • Redirects show up as errors. httpx doesn't follow redirects unless you pass follow_redirects=True, and raise_for_status() raises on a 3xx ("Redirect response '301 Moved Permanently'"). When an API moves, update the URL. Turn redirects on only when you mean to.
  • httpx has a default timeout, and timeout=None removes it. By default httpx waits 5 seconds at each stage: connecting, reading, writing and getting a connection from the pool. (The requests library has no default timeout.) If you pass timeout=None to fix slow calls, one hung connection can stall a whole batch forever. Set timeouts explicitly. Give slow endpoints, such as LLM APIs, a much longer read timeout instead of none.
  • Honor Retry-After, cap it, and add jitter. 429 and 503 responses often include Retry-After, as a number of seconds or as an HTTP date. Wait at least that long, up to a cap you choose; past the cap, give up and report the failure. Add random jitter to the exponential backoff, so 50 workers that failed at the same moment don't all retry in the same millisecond.
  • Retry only idempotent calls automatically. After a timeout on a POST, you can't tell whether the server created the record. Retrying creates duplicates unless the API accepts an idempotency key (send the same key on every attempt), or you check whether the record exists before creating it again. In HTTP, GET, PUT and DELETE are idempotent; POST is not.
Exercise 1

A ZIP lookup client with retries

~50 min

In code/week-0B/ex1-zip/zipclient.py, write lookup_zip(client, zip_code, retries=3):

  1. GET https://api.zippopotam.us/us/{zip} with a 5-second timeout.
  2. Return None for 404, and {"city": ..., "state": ...} for a hit.
  3. Retry transport errors, 429 and 5xx responses up to retries times with exponential backoff (for a 429, wait the Retry-After seconds when the server sends them), logging a WARNING each time; re-raise after the last attempt. Never retry other 4xx errors.
  4. Try it on 75024, 02108 and 00000.

Check: 75024 → {"city": "Plano", "state": "TX"}; 00000 → None. On Day 3 you'll test it without the internet.

Pass the client in rather than creating it inside. That makes the function reusable (one connection pool) and testable (you can pass a fake client later). Wrap the request in a for attempt in range(...) loop; try the call, and in except decide whether this error is worth retrying.
for attempt 1..retries: try: resp = get; if 404 → None; raise_for_status; return parsed → except TransportError or HTTPStatusError: retryable = transport error or status 429 or status ≥ 500; if last attempt or not retryable → raise; wait = Retry-After (for a 429 that sends it) or 0.5 × 2^(attempt-1); log warning; sleep(wait)
except (httpx.TransportError, httpx.HTTPStatusError) as e:
    status = e.response.status_code if isinstance(e, httpx.HTTPStatusError) else None
    retryable = status is None or status == 429 or status >= 500   # None: a transport error
    if attempt == retries or not retryable:
        raise
import logging
import time

import httpx

logger = logging.getLogger(__name__)
BASE_URL = "https://api.zippopotam.us/us/"


def lookup_zip(client: httpx.Client, zip_code: str, retries: int = 3) -> dict | None:
    """Return {"city", "state"} for a US ZIP, None if the ZIP doesn't exist.
    Retries network errors, 429 and 5xx responses; raises after the last attempt."""
    for attempt in range(1, retries + 1):
        try:
            resp = client.get(BASE_URL + zip_code, timeout=5.0)
            if resp.status_code == 404:
                return None
            resp.raise_for_status()
            place = resp.json()["places"][0]
            return {"city": place["place name"], "state": place["state abbreviation"]}
        except (httpx.TransportError, httpx.HTTPStatusError) as e:
            status = e.response.status_code if isinstance(e, httpx.HTTPStatusError) else None
            retryable = status is None or status == 429 or status >= 500   # None: a transport error
            if attempt == retries or not retryable:
                raise
            wait = 0.5 * 2 ** (attempt - 1)
            retry_after = e.response.headers.get("Retry-After", "") if status == 429 else ""
            if retry_after.isdigit():                  # the server says how long to wait
                wait = float(retry_after)
            logger.warning("Attempt %s for %s failed (%s); retrying in %.1fs", attempt, zip_code, e, wait)
            time.sleep(wait)
    return None


if __name__ == "__main__":
    with httpx.Client() as client:
        for z in ["75024", "02108", "00000"]:
            print(z, lookup_zip(client, z))

  3. In code/week-0B/ts/lead.ts, write parseCreditScore(raw: string): number that throws an Error for empty input, non-whole numbers, and values outside 300–850, just like your Python version.
function parseCreditScore(raw: string): number {
  if (raw.trim() === "") throw new Error("credit_score is missing");
  const score = Number(raw);
  if (!Number.isInteger(score)) throw new Error(`not a whole number: ${raw}`);
  if (score < 300 || score > 850) throw new Error(`credit_score ${score} is outside 300-850`);
  return score;
}

Core · Pydantic

Last week you wrote about 60 lines of validation by hand. Pydantic lets you declare the shape and rules of your data as a class, and it does the converting, checking and error reporting for you. It's used everywhere in the agent world: FastAPI, the OpenAI and Claude SDKs, LangChain, and structured LLM output (Week 1).

(.venv) $ pip install pydantic
from datetime import date
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, ValidationError, field_validator


class Lead(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True)   # trim every string

    lead_id: str = Field(min_length=1)
    credit_score: int = Field(ge=300, le=850)       # "742" is converted to 742
    loan_amount: float = Field(gt=0, le=5_000_000)
    loan_type: Literal["purchase", "refinance"]     # only these two values
    created_at: date                                # "2026-09-31" is rejected
    zip: str = Field(pattern=r"^\d{5}$")            # stays a string: keeps "02108"

    @field_validator("loan_type", mode="before")    # runs BEFORE type checking
    @classmethod
    def lower_loan_type(cls, v):
        return v.strip().lower() if isinstance(v, str) else v


try:
    lead = Lead(lead_id="L-1", credit_score="905", loan_amount="385000",
                loan_type="Purchase", created_at="2026-09-01", zip="75024")
except ValidationError as e:
    for err in e.errors():
        print(err["loc"][0], "→", err["msg"])      # credit_score → Input should be less than or equal to 850
  • Constraints go in Field(...): ge/le (≥/≤), gt, min_length, pattern.
  • Custom rules go in a @field_validator that raises ValueError. Pydantic collects all errors, not just the first.
  • e.errors() gives a list of dicts with loc (which field) and msg, ready for your report.
  • lead.model_dump(mode="json") turns the model back into JSON-ready data (dates become strings).
  • Some rules need context from other rows, like duplicate IDs. Those stay outside the model.
Production reality
  • Lax mode accepts more than you expect. An int field accepts "742.0", " 742 ", "1_000" and True (as 1). A plain float field accepts "nan", "inf" and "3e5". Add range constraints (ge/le reject NaN). Use Field(strict=True) where the exact type matters, or a before validator that checks the raw string.
  • Renamed columns fail with a misleading message. Pydantic ignores extra keys by default. If a customer renames credit_score to fico, every row fails with "Field required", and nothing mentions the new column. With ConfigDict(extra="forbid"), the error also says "Extra inputs are not permitted" for fico, which points to the real cause. Better still, compare the CSV header with the model's fields once, before reading any rows.
  • Error messages are written for developers. Each entry in e.errors() has a stable type (int_parsing, missing, greater_than_equal) and the rejected input, as well as msg. Map the types to plain messages for the sales team, and put the rejected value in the report so people can find the bad cell.
  • Where the data comes from decides its types. csv gives you strings; pandas and JSON APIs give you numbers. A str field rejects the int 75024 ("Input should be a valid string"). ConfigDict(coerce_numbers_to_str=True) would turn 2108 into "2108", which is still wrong. Fix the type where you read the data (dtype=str), not in the model.
  • NaN spreads quietly. If a float("nan") gets past validation, SQLite stores it as NULL and pandas leaves it out of means, so averages quietly use a smaller count. Reject it where the data comes in, with a range constraint or ConfigDict(allow_inf_nan=False).

Enterprise · TypeScript II: interfaces and unions

An interface describes the shape of an object (like a Pydantic model without the runtime checks). A union of literal types restricts a value to a fixed set, like Python's Literal. Add these to lead.ts and run it with node lead.ts:

type LoanType = "purchase" | "refinance";

interface Lead {
  leadId: string;
  creditScore: number;
  loanType: LoanType;
  zip: string;
}

function parseLoanType(raw: string): LoanType {
  const v = raw.trim().toLowerCase();
  if (v === "purchase" || v === "refinance") return v;   // TypeScript narrows v to LoanType here
  throw new Error(`unknown loan type: ${raw}`);
}

const lead: Lead = { leadId: "L-1001", creditScore: parseCreditScore("742"),
                     loanType: parseLoanType("Purchase"), zip: "75024" };
console.log(lead);
Important differenceTypeScript types are checked while you write code and then erased. At run time nothing validates the data. If a value comes from an API, you still need runtime checks, which is why functions like parseLoanType exist.

Testing code that calls an API, without the internet

Tests must be fast and never depend on someone else's server. httpx lets you swap the network for a function that returns fake responses:

import httpx
from zipclient import lookup_zip


def fake_api(request: httpx.Request) -> httpx.Response:
    if request.url.path.endswith("/75024"):
        return httpx.Response(200, json={"places": [{"place name": "Plano", "state abbreviation": "TX"}]})
    return httpx.Response(404, json={})


def test_lookup_zip_found_and_missing():
    client = httpx.Client(transport=httpx.MockTransport(fake_api))
    assert lookup_zip(client, "75024") == {"city": "Plano", "state": "TX"}
    assert lookup_zip(client, "00000") is None

This is why Exercise 1 took the client as a parameter. For files, pytest gives each test a fresh temporary folder: add a tmp_path argument and write there.

Production reality
  • A blocking call freezes every coroutine. time.sleep, requests.get or a sync httpx.Client inside async code stops the whole event loop: 20 one-second backoffs take 20 s instead of overlapping. Use await asyncio.sleep and httpx.AsyncClient, and run blocking work you can't avoid with await asyncio.to_thread(...).
  • A semaphore limits concurrency, not rate. Semaphore(5) with 50 ms responses still allows about 100 requests per second. If the provider limits requests per second or per minute, add a rate limiter or space out your requests, and still handle 429.
  • By default, gather loses work. Without return_exceptions=True, the first exception reaches your await, while the other tasks keep running and their results are thrown away. Either collect exceptions per item (return_exceptions=True, then pair each result with its input), or use asyncio.TaskGroup (Python 3.11+), which cancels the remaining tasks when one fails.
  • Mocks don't simulate time. MockTransport never enforces timeouts, so a handler that sleeps just makes the test slow. To test those paths, raise httpx.ReadTimeout or httpx.ConnectError in the handler. Pass the sleep function in as a parameter, so a retry test doesn't spend 1.5 s in backoff.
  • Shared async objects break between tests. An asyncio.Semaphore created at module level is tied to the first event loop that has to make a task wait on it. A second asyncio.run() in another test can then fail with "is bound to a different event loop". Create semaphores and clients inside the function that runs the loop.

Core · async / await

Looking up 1,000 ZIP codes one at a time spends almost all its time waiting on the network. async lets one program wait on many requests at once. Agents use this to call several tools or models in parallel.

import asyncio
import httpx


async def lookup_one(client: httpx.AsyncClient, sem: asyncio.Semaphore, zip_code: str):
    async with sem:                                   # at most N requests in flight
        resp = await client.get(f"https://api.zippopotam.us/us/{zip_code}", timeout=5.0)
        ...


async def lookup_many(zips: list[str], limit: int = 5) -> dict:
    sem = asyncio.Semaphore(limit)                    # be polite: don't flood the API
    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(*(lookup_one(client, sem, z) for z in set(zips)))
    return dict(results)


print(asyncio.run(lookup_many(["75024", "02108", "00000"])))
  • async def makes a function a coroutine; await pauses it while it waits, so other coroutines can run.
  • asyncio.gather runs many coroutines at once and returns their results in order.
  • A Semaphore caps how many run at the same time, which keeps you under the API's rate limit.
  • asyncio.run(...) starts everything from normal (non-async) code.

        resp = await client.get(BASE_URL + zip_code, timeout=5.0)
        if resp.status_code == 404:
            return zip_code, None
        resp.raise_for_status()
        place = resp.json()["places"][0]
        return zip_code, {"city": place["place name"], "state": place["state abbreviation"]}


async def lookup_many(zips: list[str], limit: int = 5, transport=None) -> dict[str, dict | None]:
    sem = asyncio.Semaphore(limit)
    async with httpx.AsyncClient(transport=transport) as client:
        results = await asyncio.gather(*(lookup_one(client, sem, z) for z in set(zips)))
    return dict(results)

Core · SQLite from Python

SQLite is a full SQL database in a single file, built into Python. The SQL you learn here works (with small differences) on Postgres, Snowflake and the warehouses your customers use.

import sqlite3

conn = sqlite3.connect("out/leads.db")            # creates the file if needed; ":memory:" for tests
conn.execute("""
CREATE TABLE IF NOT EXISTS leads (
    lead_id        TEXT PRIMARY KEY,
    credit_score   INTEGER NOT NULL,
    property_state TEXT NOT NULL
)""")

rows = [{"lead_id": "L-1001", "credit_score": 742, "property_state": "TX"}]
conn.executemany(
    "INSERT OR REPLACE INTO leads VALUES (:lead_id, :credit_score, :property_state)",   # named parameters
    rows,
)
conn.commit()                                       # nothing is saved until you commit

for state, n in conn.execute("SELECT property_state, COUNT(*) FROM leads GROUP BY property_state"):
    print(state, n)
Never build SQL with f-stringsf"SELECT * FROM leads WHERE email = '{email}'" lets a crafted input like ' OR '1'='1 rewrite your query. That's SQL injection, one of the most exploited bugs in history. Always pass values as parameters (? or :name) and let the driver handle them. Agents that generate SQL (Week 19) make this even more important.

Core · Branches and pull requests

On a team, and at a customer, you never push straight to main. You work on a branch, open a pull request (PR), someone reviews the diff, then it's merged. You'll do this for every project from now on, even alone: reviewing your own diff catches mistakes.

$ git switch -c add-sqlite-store          # new branch
# … edit, test, commit …
$ git push -u origin add-sqlite-store
$ gh pr create --fill                      # open a PR from your commits
$ gh pr diff                               # review your own changes line by line
$ gh pr merge --squash --delete-branch     # merge when it's right
$ git switch main && git pull

A good PR description says what changed, why, and how you tested it.

Production reality
  • A missing commit can pass your tests. A connection sees its own uncommitted rows, so a test that uses a single :memory: connection passes, while the real database file ends up with an empty table. (In Python's default mode, CREATE TABLE takes effect at once; inserts wait for a commit.) Test storage by reopening a tmp_path file with a new connection.
  • A failed batch can leave some rows behind. If executemany fails on row 5 of 9, rows 1–4 stay in the open transaction, and a later commit() saves them. Use with conn: so an exception rolls the whole batch back, and give every row dict every key (city=None).
  • SQLite converts column types quietly. A column declared INTEGER stores "02108" as 2108. A STRICT table does the same; it only rejects text that can't become a number. Declare identifiers such as ZIPs, phone numbers and IDs as TEXT. Integer division truncates too: SUM(credit_score)/COUNT(*) gives 747 for TX, not 747.25. Use AVG, or multiply by 1.0 first.
  • Placeholders bind values, never names. ORDER BY ? sorts by a constant string, so the order is silently wrong, and an f-string column name can be injected. Check table and column names against an allowlist. Also, a JOIN multiplies rows: a ZIP with two places counts its lead twice, so compare COUNT(*) with COUNT(DISTINCT lead_id).
  • Merging a PR doesn't erase what it contained. Commits pushed to a PR branch are still visible on GitHub after a squash merge, even after the branch is deleted. A key that was ever pushed must be revoked; deleting the file isn't enough. After a squash merge, git branch -d also refuses to delete your local branch; gh pr merge --squash --delete-branch deletes both the local and the remote branch.

CREATE TABLE IF NOT EXISTS leads (

def leads_per_state(conn: sqlite3.Connection) -> list[tuple[str, int, float]]:

        "SELECT property_state, COUNT(*), ROUND(AVG(credit_score), 1) FROM leads "

Six bugs in an API enrichment and storage package

~60 min

Download ⬇ enrich-drill.zip, unzip it, read its README, and run the tests. The code runs, but six tests fail. Each failure is a mistake that shows up in real projects. Fix the code, never the tests, and for each bug write one line in BUGS.md: what was wrong, what a user would have seen in production, and how you fixed it.

Check: all 15 tests pass, offline. Then explain each bug out loud in one sentence, as you would to an interviewer who asks "how would this fail in production?"

Read each failing test's name and assertion before opening the code. The bugs are in zipclient.py, enrich.py, store.py, models.py.
  1. zipclient.py: retryable was true for every status of 400 or more, so a 400 Bad Request (and a 401 or 403) was sent three times with backoff before failing. In production, a bad ZIP or a bad API key costs extra calls and seconds of waiting, and an API that counts failed calls can throttle you. Fix: retry only transport errors, 429 and 5xx: retryable = status is None or status == 429 or status >= 500.
  2. enrich.py: the AsyncClient was created with timeout=None, which turns off httpx's default 5-second timeout. One hung connection would stall the whole enrichment run forever instead of becoming a warning. Fix: pass an explicit timeout (timeout=5.0).
  3. enrich.py: _lookup created its own asyncio.Semaphore(limit), so each task had a private semaphore and nothing was shared: all 20 requests ran at once. Against the real API that means rate-limit errors (429) or a ban. Fix: create one semaphore in enrich_leads and pass it to every _lookup.
  4. store.py: the INSERT was built by pasting values into the SQL string. "Ryan O'Connor" ends the string early and crashes the save with OperationalError: near "Connor": syntax error, and a crafted name or email could rewrite the query (SQL injection). Fix: conn.executemany(INSERT, rows) with named parameters (:lead_id, :full_name, …).
  5. store.py: save_leads never called conn.commit(). The same connection saw the rows, so a test on one :memory: connection passed, but the inserts were rolled back when the program ended: the leads table existed and was empty. Fix: commit after executemany (or wrap it in with conn:).
  6. models.py: zip was an int, so "02108" became 2108 and "00000" became 0. The Boston lead (L-1019) was looked up as ZIP 2108, got a 404, and was reported as "ZIP 2108 not found" instead of getting its city. Fix: keep ZIPs as strings: zip: str = Field(pattern=r"^\d{5}$").

Q1

Design a sync system between two employee record systems.

Palantir · Forward Deployed Software Engineer · decomposition

Reported Prep-site guide: Exponent ↗. Palantir describes the role's "technical decomposition" skill in Dev versus Delta ↗. Secondary source; not an official question.

What it probes: Whether you break a vague integration into its parts: identity, change capture, validation, conflicts and operations. It's the same shape as this week's pipeline: call an API, validate, store, and handle failures.

  1. Clarify first: which systems (an HR platform and a legacy database?), one-way or two-way, which system owns which field, how many records, how fresh the data must be (nightly or within minutes), and who is allowed to see personal data.
  2. Identity: a stable key to match records on. If the systems use different IDs, keep a mapping table, and decide what happens with duplicates or records you can't match.
  3. Change capture: polling with an "updated since" cursor, webhooks, or full snapshots compared with the last one. Handle paging, rate limits, retries with backoff (429 and 5xx only), and idempotent upserts keyed by ID, so a rerun never creates duplicates.
  4. Validation: a model per system (like your Pydantic Lead), normalized formats (dates, phone numbers and ZIPs as strings), and a quarantine list of bad records with reasons, instead of failing the whole run.
  5. Conflicts and deletes: per-field ownership or last-writer-wins by timestamp; in a two-way sync, don't send a change back to the system it came from; terminations become soft deletes, not missing rows.
  6. Operations: an audit log of every change, a dry-run mode, a nightly reconciliation that compares counts and per-field checksums, and alerts when they drift.

Answers that fail:

  • "Copy the table every night" with no plan for identity, conflicts or deletes.
  • Assuming both systems share an ID and the same field formats.
  • Never mentioning personal data, access or an audit trail.

Q3

Why did you choose this approach, and where did you decide against another path? (Practice it on your Lead Intake v2.)

Reported Prep-site guide: Exponent ↗ reports this as the follow-up after the take-home ("Build a semantic search over a product catalog that ChatGPT can query, then walk through your system"). Here you practice it on this week's project. Secondary source.

Q5

Design a service that enriches 5 million leads a day with location data from a third-party API that allows 10 requests per second.

AWS · Solutions Architect · system design (format practice)

Format practice Original practice question in the style of Amazon's system design round, described in Amazon's SDE II interview prep page ↗ (judged on practicality, accuracy, efficiency, reliability, optimization and scalability). Not a reported question.

What it probes: Arithmetic first, then the parts this week introduced, at scale: rate limits, retries, idempotent writes, and failures that become warnings instead of outages.

  1. Clarify: does enrichment have to happen in real time or can it run in batches? How fresh must the data be? Do the API's terms allow caching? What happens to a lead that can't be enriched?
  2. Do the arithmetic: 10 requests per second × 86,400 s = 864,000 calls a day, far below 5 million. One call per lead can't work.
  3. Deduplicate and cache by ZIP: US ZIP codes number in the tens of thousands, so almost every lookup is a cache hit. Only new ZIPs use the rate budget.
  4. Pipeline: a queue of lead IDs, workers that share one global rate limiter (a token bucket, not just a per-worker semaphore), retries only for 429 and 5xx with backoff and Retry-After, and a dead-letter queue for records that keep failing.
  5. Writes are idempotent upserts keyed by lead_id, so replays and retries never create duplicates. Leads flow to sales even when the API is down; a backfill job fills in cities later.
  6. Monitoring: enrichment rate, cache hit rate, 429 count, warning rate and queue depth, with alerts on sudden changes.

Answers that fail:

  • No arithmetic, so the 10 requests per second limit is never noticed.
  • "Add more workers" to go faster against a fixed rate limit, which causes retry storms.
  • Blocking lead intake whenever the enrichment API fails.
Q6

What questions would you ask customers before designing? (Practice it on: "Sales wants every lead cleaned, enriched with a city and stored so an agent can query it.")

OpenAI · Forward Deployed Engineer · interview loop

Reported Candidate write-up (March 2026): gaijineer.co ↗. Secondary source; not an official question. The scenario is this week's project.

What it probes: Whether you find out about the data, the users and what counts as success before choosing tools, and whether you put your questions in a sensible order.

  1. Ask for a real sample file first, then about the data: where the leads come from, how many a day, who produces the CSV, and which values are known to be messy.
  2. Definitions: what makes a lead valid, which duplicate wins, and whether a missing city is acceptable.
  3. Users: who reads the results (reps, managers, the Week 1 agent), and which questions they will ask of the data.
  4. Constraints: personal data rules, where the data may be stored, how long it's kept, and the security review process.
  5. Success: the business number that should improve (fewer lost leads, faster first contact), and how you'd measure it.
  6. Failure handling and integration: who fixes invalid rows, whether the CRM stays the system of record, and whether results must be written back to it.

Answers that fail:

  • Asking only about technology ("Postgres or SQLite?").
  • Never asking what success looks like, or who owns bad data.
  • A long unordered list with no sense of which question matters most.
