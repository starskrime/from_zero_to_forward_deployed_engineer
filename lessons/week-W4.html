Should You Build Single Agents or Multi Agent Systems? ↗

The AI Daily Brief: Artificial Intelligence News · 2025 · 11:47

Both sides of the debate: Anthropic's multi-agent research system, then from 4:28 Cognition's two principles (share full context and traces; actions carry implicit decisions) and when each design fits.

Reference (optional)
  • Cognition: Don't Build Multi-Agents ↗

Summary

  • Where one agent breaks down: too many tools to choose from, a context that fills with every search result, and instructions for several jobs that pull against each other. Symptoms: wrong tool choices, forgotten constraints, and cost that grows with every turn.
  • Workflows vs agents (Anthropic's definitions): in a workflow, code decides the path and models fill in steps; in an agent, the model decides its own steps and tool calls. The workflow patterns: prompt chaining, routing, parallelization (sectioning or voting), orchestrator–workers, evaluator–optimizer. Most "multi-agent systems" in production are one of these.
  • The case for a team: Anthropic's research system (a lead agent on Claude Opus 4 with Sonnet 4 subagents) beat a single Opus 4 agent by 90.2% on their internal research eval, mostly by spending more tokens in parallel. Agents use about 4× the tokens of a chat, and their multi-agent system about 15×.
  • The case against: Cognition's two principles: share full context and traces, and actions carry implicit decisions, so two agents deciding separately make conflicting choices. Anthropic agrees that tasks where every agent needs the same context, or with many dependencies between agents (most coding), fit badly.
  • The rule you'll use: split when sub-tasks are independent (they can run in parallel without talking) and each needs less context than the whole. Keep one agent when steps depend on each other's decisions.
  • Code for math, models for language. Routes, battery percentages, charging minutes and "is this charger working?" are deterministic: write them as functions, test them, and give them to agents as tools. A model that does arithmetic in its head will eventually get it wrong in front of a customer.
Production reality
  • Every agent is another bill. Each sub-agent re-reads its own instructions and inputs on every call. A five-agent pipeline that looks tidy in a diagram can cost several times a single call; log tokens per agent from day one (Exercise 2 does).
  • Hand-offs lose information. When a coordinator writes a one-line task for a sub-agent, everything it didn't write is gone. Cognition's example: two sub-agents asked to build parts of a Flappy Bird clone produced a Super Mario background and a bird that didn't match. Pass structured inputs, not prose summaries.
  • Greedy is optimal only for the simple case. "Drive as far as possible, charge at the last charger before you run out" gives the fewest stops for one car on a fixed route. It does not minimize total time once charger speeds differ, and it can't choose between routes. Say which property your algorithm guarantees.
  • Data has holes. Two of Norvale's 17 chargers are out of service, one town's only charger fits one connector type, and one mountain road is longer than a small car can drive. Real charger data is worse. Every plan needs an independent validator that re-checks it from the raw data.
  • "Can't be done" is a valid answer. A planner that always returns a plan will invent one. Make infeasibility a first-class result with a reason, and try alternatives (another route) before giving up.
Exercise 1

The deterministic core: routes, energy, charging

~80 min

In code/week-4/road_trip/network.py, write the functions every agent will use as tools:

  1. load_network(path) and shortest_route(net, origin, destination, avoid_roads=frozenset()): Dijkstra on kilometers, skipping roads named in avoid_roads. Return a Route with its towns and legs.
  2. usable_chargers(net, town, connector): available chargers with the car's connector, fastest first.
  3. charge_minutes(vehicle, charger, soc_from, soc_to): power is the lower of the charger's and the car's maximum; above 80% charge, speed drops to 40% of that power.
  4. plan_charging(net, route, vehicle, start_soc, reserve=0.10, charge_to=0.80, towing=False): the greedy plan. Never arrive anywhere below the reserve; charge to 80%, or to 100% when 80% can't reach the next usable charger or the destination; you may charge at the origin. Return an infeasible plan with a reason when the trip can't be driven.
  5. validate(net, route, vehicle, plan, start_soc, reserve, towing): re-check any plan leg by leg (reserve, charger status, connector) and return a list of problems.

Check: Ashford → Kestrel Point is 540 km via Millbrook, Harlow, Ironbridge and Fairhaven. For the Voltra City at 90%: stop at CH-10 in Harlow (26% → 100%, 31 minutes: Ironbridge's only charger is NACS, and 80% can't reach Fairhaven) and CH-08 in Fairhaven (20% → 80%, 18 minutes); arrival at 51%; validate returns []. charge_minutes for 20% → 80% on a 350 kW charger is 18.0 minutes, and 80% → 100% is 15.0. Cedar Falls → Wolf Ridge in the Voltra City at 90% is infeasible: from Glenrock nothing is in range, even at 100%.

Keep cumulative kilometers along the route (cum[j] - cum[i] is the distance between towns i and j), and a helper that returns the charge after driving from i to j. Greedy loop: if the destination is reachable with the reserve, stop; otherwise pick the farthest town with a usable charger you can reach, charge there, repeat. For Dijkstra, push (distance, town, path) onto a heap; ties then break alphabetically, which keeps results deterministic.
"""Deterministic trip math: routes, energy and charging stops. No model calls here."""
import heapq
import json
from dataclasses import dataclass, field
from pathlib import Path

TAPER_FROM = 0.80          # above 80% state of charge, charging slows down...
TAPER_SPEED = 0.40         # ...to 40% of the power
DRIVE_KMH = 80             # average speed for time estimates


@dataclass
class Network:
    towns: list[str]
    roads: dict[str, list[tuple[str, int, str]]]     # town -> [(neighbor, km, road name)]
    chargers: list[dict]
    vehicles: dict[str, dict]
    places: list[dict]


def load_network(path: Path) -> Network:
    raw = json.loads(Path(path).read_text())
    roads: dict[str, list] = {t: [] for t in raw["towns"]}
    for r in raw["roads"]:
        roads[r["a"]].append((r["b"], r["km"], r["road"]))
        roads[r["b"]].append((r["a"], r["km"], r["road"]))
    return Network(raw["towns"], roads, raw["chargers"], {v["id"]: v for v in raw["vehicles"]}, raw["places"])


@dataclass
class Route:
    towns: list[str]
    legs: list[tuple[str, str, int, str]]            # (from, to, km, road)

    @property
    def km(self) -> int:
        return sum(leg[2] for leg in self.legs)


def shortest_route(net: Network, origin: str, destination: str, avoid_roads: frozenset = frozenset()) -> Route:
    """Dijkstra on road km, skipping any road named in avoid_roads. Ties break alphabetically."""
    for town in (origin, destination):
        if town not in net.roads:
            raise ValueError(f"unknown town: {town}")
    queue, done = [(0, origin, [origin])], set()
    while queue:
        dist, town, path = heapq.heappop(queue)
        if town == destination:
            legs = []
            for a, b in zip(path, path[1:]):
                km, road = next((k, r) for n, k, r in net.roads[a] if n == b)
                legs.append((a, b, km, road))
            return Route(path, legs)
        if town in done:
            continue
        done.add(town)
        for nxt, km, road in net.roads[town]:
            if nxt not in done and road not in avoid_roads:
                heapq.heappush(queue, (dist + km, nxt, path + [nxt]))
    raise ValueError(f"no road from {origin} to {destination}")


def kwh_per_km(vehicle: dict, towing: bool = False) -> float:
    factor = vehicle.get("towing_factor", 1.0) if towing else 1.0
    return vehicle["kwh_per_100km"] / 100 * factor


def usable_chargers(net: Network, town: str, connector: str) -> list[dict]:
    """Chargers in a town that work and fit the car, fastest first."""
    return sorted((c for c in net.chargers if c["town"] == town and c["status"] == "available"
                   and connector in c["connectors"]), key=lambda c: (-c["power_kw"], c["id"]))


def charge_minutes(vehicle: dict, charger: dict, soc_from: float, soc_to: float) -> float:
    power = min(charger["power_kw"], vehicle["max_charge_kw"])
    below = max(0.0, min(soc_to, TAPER_FROM) - soc_from) * vehicle["battery_kwh"]
    above = max(0.0, soc_to - max(soc_from, TAPER_FROM)) * vehicle["battery_kwh"]
    return (below / power + above / (power * TAPER_SPEED)) * 60


@dataclass
class Stop:
    town: str
    charger_id: str
    arrive_soc: float
    depart_soc: float
    kwh: float
    minutes: float
    cost: float


@dataclass
class ChargePlan:
    feasible: bool
    stops: list[Stop] = field(default_factory=list)
    arrival_soc: float = 0.0
    reason: str = ""

    @property
    def charging_minutes(self) -> float:
        return sum(s.minutes for s in self.stops)


def plan_charging(net: Network, route: Route, vehicle: dict, start_soc: float, reserve: float = 0.10,
                  charge_to: float = 0.80, towing: bool = False) -> ChargePlan:
    """Greedy: drive as far as the reserve allows, charge at the farthest usable charger before that point.
    For one car on a fixed route this gives the fewest stops."""
    per_km = kwh_per_km(vehicle, towing)
    towns, cum = route.towns, [0]
    for leg in route.legs:
        cum.append(cum[-1] + leg[2])

    def soc_after(i: int, j: int, soc: float) -> float:          # drive from town i to town j
        return soc - (cum[j] - cum[i]) * per_km / vehicle["battery_kwh"]

    def chargers_at(j: int) -> list[dict]:
        return usable_chargers(net, towns[j], vehicle["connector"])

    stops, i, soc = [], 0, start_soc
    while True:
        if soc_after(i, len(towns) - 1, soc) >= reserve:
            return ChargePlan(True, stops, round(soc_after(i, len(towns) - 1, soc), 3))
        first = i if not stops and i == 0 else i + 1          # the origin's own charger counts, once
        reachable = [j for j in range(first, len(towns) - 1)
                     if (j == i or soc_after(i, j, soc) >= reserve) and chargers_at(j)]
        if not reachable:
            return ChargePlan(False, stops, reason=f"no usable charger within range after {towns[i]}")
        j = reachable[-1]
        if j == i and soc >= charge_to:
            return ChargePlan(False, stops, reason=f"no usable charger within range after {towns[i]}")
        arrive = soc_after(i, j, soc)
        target = charge_to
        # if charge_to can't reach any usable charger or the destination beyond j, charge fuller
        def progress(depart: float) -> bool:
            if soc_after(j, len(towns) - 1, depart) >= reserve:
                return True
            return any(soc_after(j, k, depart) >= reserve and chargers_at(k) for k in range(j + 1, len(towns) - 1))
        if not progress(target):
            target = 1.0
            if not progress(target):
                return ChargePlan(False, stops, reason=f"from {towns[j]}, no usable charger or the destination is in range, even at 100%")
        charger = chargers_at(j)[0]
        depart = max(arrive, target)
        kwh = (depart - arrive) * vehicle["battery_kwh"]
        stops.append(Stop(towns[j], charger["id"], round(arrive, 3), round(depart, 3), round(kwh, 1),
                          round(charge_minutes(vehicle, charger, arrive, depart), 1),
                          round(kwh * charger["price_per_kwh"], 2)))
        i, soc = j, depart


def validate(net: Network, route: Route, vehicle: dict, plan: ChargePlan, start_soc: float,
             reserve: float = 0.10, towing: bool = False) -> list[str]:
    """Independent checks the critic runs on ANY plan, including one a model edited."""
    problems, per_km = [], kwh_per_km(vehicle, towing)
    by_id = {c["id"]: c for c in net.chargers}
    stops = {s.town: s for s in plan.stops}
    soc = start_soc
    if route.towns[0] in stops:                                  # charging before leaving
        soc = max(soc, stops[route.towns[0]].depart_soc)
    for a, b, km, _ in route.legs:
        soc -= km * per_km / vehicle["battery_kwh"]
        if soc < reserve - 1e-9:
            problems.append(f"arrives in {b} with {soc:.0%}, below the {reserve:.0%} reserve")
        if b in stops:
            s = stops[b]
            c = by_id.get(s.charger_id)
            if c is None or c["town"] != b:
                problems.append(f"{s.charger_id} is not a charger in {b}")
            else:
                if c["status"] != "available":
                    problems.append(f"{c['id']} in {b} is {c['status']}")
                if vehicle["connector"] not in c["connectors"]:
                    problems.append(f"{c['id']} in {b} has no {vehicle['connector']} connector")
            if s.depart_soc > 1.0:
                problems.append(f"departs {b} above 100%")
            soc = max(soc, s.depart_soc)
    unknown = [s.town for s in plan.stops if s.town not in route.towns]
    problems += [f"stop in {t} is not on the route" for t in unknown]
    return problems

Certification · Task 1.2: coordinator and subagents

  • Hub and spoke: a coordinator (the main agent) delegates focused tasks to subagents and combines their results. Subagents report to the coordinator, not to each other.
  • Isolated context: in the Claude Agent SDK, a subagent starts with a fresh conversation. It gets its own system prompt and the prompt string the coordinator wrote for it, not the parent's history, tool results or system prompt. Its intermediate tool calls stay inside it; only its final message returns to the parent.
  • Why that matters: a subagent can read dozens of files without filling the coordinator's context, and it can't use facts it was never given. Exam questions often describe a subagent that "forgot" something the user said: the coordinator never passed it.
  • Specialized and restricted: each subagent gets its own instructions and can be limited to a few tools (a reviewer that can read but not edit).

Enterprise · OAuth 2.0: roles, flows and PKCE

Every enterprise integration you build asks "who is calling, and what may they do?" OAuth 2.0 answers the second half with access tokens. The roles: the resource owner (the user), the client (your app or agent), the authorization server (Okta, Entra ID) and the resource server (the API). Two flows cover most FDE work: the authorization code flow with PKCE when a user signs in, and client credentials when a service acts as itself. The current security guidance (RFC 9700, January 2025) says clients should not use the implicit grant, public clients must use PKCE (and it's recommended for all), and the password grant must not be used at all.

PKCE in one line: the client makes a random verifier, sends its SHA-256 hash (the challenge) with the login request, and sends the verifier itself when it exchanges the code, so a stolen code is useless. Summary

  • Five roles for P3: an intake agent turns the driver's words into a TripSpec; the planner is code (Day 1); one stop guide per charging stop suggests what to do there; a writer turns the plan into an itinerary; a critic checks the result. Only three of the five need a model.
  • Hand-offs are data, not prose. Each agent returns a Pydantic model (structured output, Week 0C), and the next one receives exactly the fields it needs. You can test every boundary without a model.
  • Slice the context. A stop guide needs one town's guidebook entries, the minutes available and the interests: about 165 characters. The trip's spec, route and plan plus every charger and place come to about 5,200. Less context means lower cost and fewer ways to go wrong.
  • The critic is code where it can be. "Does the itinerary mention exactly the planned chargers?" and "does every leg keep the reserve?" are checks, not opinions. A model critic can be argued with; a failing assert can't. That's the evaluator–optimizer pattern with a deterministic evaluator.
  • Bound every loop. Writer → critic → writer runs at most three times, then hands the problem to a human. An unbounded revision loop is how agent bills explode.
  • Test parallel agents by content, not order. Scripted replies that pop from one queue break as soon as two agents run at once. Route each fake reply by something in the request (the instructions, or the town name).
Production reality
  • Intake errors poison everything downstream. "90% charged" parsed as 0.09 produces a perfectly valid plan for the wrong trip. Evaluate the intake agent on its own, field by field (Weekend 2), and echo the parsed request back to the user.
  • Models invent names. A stop guide asked for "something to do" will happily suggest a restaurant that doesn't exist. Give it the list, tell it to choose only from the list, and check its answer against the list in code.
  • The writer changes numbers. Asked to "write nicely", models round 26% to "about a quarter" or swap charger ids. Give the writer a structured view with the exact values, forbid changing them, and let the critic compare ids and numbers.
  • Log per agent. Record input and output tokens (and input size) for every call, tagged with the agent's name. When the bill doubles, you need to know which agent did it.
  • Fail loudly on refusals. A structured call can come back with no parsed output (a refusal or a cut-off answer). Raise with the agent's name; a None passed along turns into a confusing error three agents later.

"""The model-backed agents. Each one gets only the context it needs, and returns structured output."""
import json
from dataclasses import asdict

from pydantic import BaseModel, Field

from road_trip.network import Network

MODEL = "gpt-6-luna"


class TripSpec(BaseModel):
    origin: str
    destination: str
    vehicle_id: str
    start_soc: float = Field(ge=0, le=1, description="state of charge at departure, 0 to 1")
    reserve: float = Field(default=0.10, ge=0.05, le=0.5, description="minimum charge on arrival anywhere")
    towing: bool = False
    interests: list[str] = Field(default_factory=list, description="food, nature, history")


class StopIdeas(BaseModel):
    town: str
    places: list[str]            # names from the guidebook only
    note: str


class Itinerary(BaseModel):
    summary: str
    steps: list[str]


def call(client, agent: str, instructions: str, payload: str, schema):
    """One structured model call. Returns (parsed, usage record) so the graph can total cost per agent."""
    r = client.responses.parse(model=MODEL, instructions=instructions, input=payload,
                               reasoning={"effort": "low"}, text_format=schema)
    if r.output_parsed is None:
        raise RuntimeError(f"{agent}: no structured output (refusal or truncation)")
    usage = {"agent": agent, "input_tokens": r.usage.input_tokens, "output_tokens": r.usage.output_tokens,
             "input_chars": len(instructions) + len(payload)}
    return r.output_parsed, usage


INTAKE = """You turn a driver's trip request into a TripSpec for Norvale's EV trip planner.
Use only these town names: {towns}. Use only these vehicle ids: {vehicles}.
If the driver gives a battery percentage, convert it to a fraction (80% -> 0.8).
If they say they are towing, set towing to true. Keep interests to: food, nature, history.
If the driver's profile below has a vehicle or interests and the request doesn't mention them, use the profile."""


def intake(client, net: Network, request: str, profile: dict | None = None):
    instructions = INTAKE.format(towns=", ".join(net.towns), vehicles=", ".join(net.vehicles))
    payload = f"Profile: {json.dumps(profile or {})}\nRequest: {request}"
    return call(client, "intake", instructions, payload, TripSpec)


STOP = """You suggest what to do during ONE charging stop on an EV road trip.
Choose at most two places from the guidebook entries given, and only ones that fit in the time available.
Prefer the driver's interests. Never invent a place that isn't listed. If nothing fits, return no places."""


def stop_context(net: Network, town: str, minutes: float, interests: list[str]) -> str:

def plan_trip(net: Network, spec) -> tuple:

    route = shortest_route(net, spec.origin, spec.destination)
    plan = plan_charging(net, route, vehicle, spec.start_soc, spec.reserve, towing=spec.towing)
    if plan.feasible:
        return route, plan, []
    tried = [f"{route.km} km via {', '.join(route.towns)}: {plan.reason}"]
    options = []
    for road in sorted({leg[3] for leg in route.legs}):
        try:
            alt = shortest_route(net, spec.origin, spec.destination, frozenset({road}))
        except ValueError:
            continue
        alt_plan = plan_charging(net, alt, vehicle, spec.start_soc, spec.reserve, towing=spec.towing)
        if alt_plan.feasible:
            options.append((alt.km / DRIVE_KMH * 60 + alt_plan.charging_minutes, alt, alt_plan))   # total minutes
    if options:
        _, route, plan = min(options, key=lambda o: o[0])
    return route, plan, tried

OAuth says what a client may do; OpenID Connect (OIDC) adds who the user is, with an ID token: a signed JWT for your app. The access token is for the API; never use one in place of the other. import base64
import hashlib
import secrets

import jwt


def pkce_pair() -> tuple[str, str]:
    verifier = secrets.token_urlsafe(64)[:96]                       # 43-128 characters
    return verifier, code_challenge(verifier)


def code_challenge(verifier: str) -> str:
    digest = hashlib.sha256(verifier.encode("ascii")).digest()
    return base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")   # S256, no padding


def verify_id_token(token: str, public_key, issuer: str, client_id: str, nonce: str) -> dict:
    claims = jwt.decode(token, public_key, algorithms=["RS256"],    # never accept the token's own "alg" blindly
                        audience=client_id, issuer=issuer, options={"require": ["exp", "iat", "sub"]})
    if claims.get("nonce") != nonce:
        raise jwt.InvalidTokenError("nonce mismatch: possible replay")
    return claims

Summary

  • A graph is your Day 2 pipeline made explicit: a typed state (a TypedDict), nodes (plain functions that take the state and return the keys they change), and edges (who runs next). START and END mark the entry and exit.
  • Reducers decide how updates merge. By default a node's value replaces the old one. For a key that several nodes write in the same step, declare a reducer: Annotated[list[dict], operator.add] appends instead. Without it, parallel writes to one key fail.
  • Conditional edges route. add_conditional_edges("plan", after_plan, [...]) calls after_plan(state), which returns the next node's name: infeasible, writer, or a list of Sends.
  • Send fans out. [Send("stop", {"town": ..., "minutes": ..., "interests": ...}) for each stop] starts one stop task per charging stop, in parallel, and each task receives only its payload, not the whole state. That's context engineering built into the framework. Their results merge through the reducer, and the next node runs once all of them finish.
  • Loops are edges back. critic → writer when there are problems and revisions are left, critic → approve when there are none. Keep the counter in the state, so the limit survives restarts (Day 4).
  • Latency: in parallel, the stop guides take as long as the slowest one, not the sum. The total cost is the same; only the waiting changes.
Production reality
  • Parallel calls meet rate limits. Ten stops fan out into ten simultaneous requests. Cap concurrency (LangGraph's max_concurrency in the run config), and keep the Week 0B retry-with-backoff in the model client.
  • One failed branch fails the step. If one parallel task raises, the whole super-step fails. Decide per agent: retry, return an empty result ("no suggestions for this stop"), or stop the trip. A missing restaurant tip should never cancel a road trip.
  • Match by key, not by position. Parallel tasks finish in any order (LangGraph then merges their updates in a fixed task order), but a stop guide that returns nothing, or a replan that changes the stops, shifts every position after it. Pair ideas with stops by town, as plan_view does.
  • State grows. Reducers that append never forget. Keep large blobs (full search results, documents) out of the graph state; store a reference or a summary.
  • A framework hides the calls. When a graph misbehaves, you need a trace of every node's input and output. Turn on tracing (LangSmith, or OpenTelemetry in Week 8) before your first customer demo, not after the first incident.

class TripState(TypedDict, total=False):
    request: str
    user_id: str
    spec: dict
    route: dict
    plan: dict
    tried: list[str]
    ideas: Annotated[list[dict], operator.add]        # written by parallel stop agents: must merge
    usage: Annotated[list[dict], operator.add]
    itinerary: str
    problems: list[str]
    revisions: int
    status: str
    booked: list[str]


def _route(d: dict) -> Route:
    return Route(d["towns"], [tuple(leg) for leg in d["legs"]])


def _plan(d: dict) -> ChargePlan:
    return ChargePlan(d["feasible"], [Stop(**s) for s in d["stops"]], d["arrival_soc"], d["reason"])


def build_graph(client, net, booking, checkpointer=None, store=None):
    def intake(state: TripState, runtime: Runtime):
        key = ("profiles", state.get("user_id", "anonymous"))
        saved = runtime.store.get(key, "profile") if runtime.store else None
        spec, u = agents.intake(client, net, state["request"], saved.value if saved else None)
        if runtime.store:                                    # remember the car and interests for next time
            runtime.store.put(key, "profile", {"vehicle_id": spec.vehicle_id, "interests": spec.interests})
        return {"spec": spec.model_dump(), "usage": [u]}

    def plan(state: TripState):
        route, plan_, tried = plan_trip(net, agents.TripSpec(**state["spec"]))
        return {"route": {"towns": route.towns, "legs": route.legs}, "plan": asdict(plan_), "tried": tried}

    def after_plan(state: TripState):
        if not state["plan"]["feasible"]:
            return "infeasible"
        stops = state["plan"]["stops"]
        if not stops:
            return "writer"
        interests = state["spec"]["interests"]
        return [Send("stop", {"town": s["town"], "minutes": s["minutes"], "interests": interests}) for s in stops]

    def stop(task: dict):                                    # receives ONLY its Send payload, not the state
        idea, u = agents.stop_ideas(client, net, task["town"], task["minutes"], task["interests"])
        return {"ideas": [idea.model_dump()], "usage": [u]}

    def writer(state: TripState):
        spec = agents.TripSpec(**state["spec"])
        view = agents.plan_view(spec, _route(state["route"]), _plan(state["plan"]), state.get("ideas", []))
        itinerary, u = agents.write_itinerary(client, view, state.get("problems", []))
        return {"itinerary": itinerary.summary + "\n" + "\n".join(itinerary.steps), "usage": [u]}

    def critic(state: TripState):
        spec = agents.TripSpec(**state["spec"])
        problems = review(net, _route(state["route"]), net.vehicles[spec.vehicle_id], _plan(state["plan"]),
                          spec, state["itinerary"])
        return {"problems": problems, "revisions": state.get("revisions", 0) + (1 if problems else 0)}

    def after_critic(state: TripState):
        if not state["problems"]:
            return "approve"
        return "writer" if state["revisions"] <= MAX_REVISIONS else "needs_human"

    def approve(state: TripState):
        # Pauses the graph. On resume the node runs again from the top, so nothing before interrupt()
        # may have side effects.
        decision = interrupt({"itinerary": state["itinerary"],
                              "reserve": [s["charger_id"] for s in state["plan"]["stops"]]})
        return {"status": "approved" if decision is True else "declined"}

    def reserve(state: TripState):
        booked = [booking.reserve(s["charger_id"], state.get("user_id", "anonymous")) for s in state["plan"]["stops"]]
        return {"booked": booked, "status": "booked"}

    g = StateGraph(TripState)
    g.add_node("intake", intake)
    g.add_node("plan", plan)
    g.add_node("stop", stop)
    g.add_node("writer", writer)
    g.add_node("critic", critic)
    g.add_node("approve", approve)
    g.add_node("reserve", reserve)
    g.add_node("infeasible", lambda s: {"status": "infeasible"})
    g.add_node("needs_human", lambda s: {"status": "needs_human"})
    g.add_edge(START, "intake")
    g.add_edge("intake", "plan")
    g.add_conditional_edges("plan", after_plan, ["stop", "writer", "infeasible"])
    g.add_edge("stop", "writer")
    g.add_edge("writer", "critic")
    g.add_conditional_edges("critic", after_critic, ["writer", "approve", "needs_human"])
    g.add_conditional_edges("approve", lambda s: "reserve" if s["status"] == "approved" else END, ["reserve", END])
    for node in ("reserve", "infeasible", "needs_human"):
        g.add_edge(node, END)
    return g.compile(checkpointer=checkpointer, store=store)

Certification · Parallel subagents and their limits

  • Parallel spawning: independent subagents (a style checker, a security scanner and a test-coverage agent) can run at the same time; the work finishes in the time of the slowest one. The coordinator asks for several Agent calls in one turn.
  • Background by default: in current Claude Code versions, subagents run in the background unless the coordinator needs the result before continuing.
  • Caps you should set: nesting depth (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, default 3 layers; 1 means subagents can't spawn their own), concurrency (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS, default 20) and spend (max_budget_usd). Subagent requests count toward the query's cost.
  • Explicit beats implicit: each parallel subagent needs its own complete prompt. "Check the other file too" means nothing to an agent that never saw the first one.

Summary

  • A checkpointer saves the state after every step, per thread (config={"configurable": {"thread_id": ...}}). With it you can pause and resume, inspect state (get_state), and survive a crash. InMemorySaver is for tests; use a database-backed saver (SQLite locally, Postgres in production) for anything real.
  • An interrupt pauses the graph for a human: decision = interrupt({"itinerary": ..., "reserve": [...]}). The run returns with __interrupt__; you resume the same thread with Command(resume=True), and that value becomes interrupt()'s return value. It needs a checkpointer and a thread id.
  • The node restarts on resume. LangGraph re-runs the whole node from its first line, not from the interrupt() call. Anything before it runs twice, so keep side effects (booking, emailing, charging a card) in a separate node after the approval.
  • A store remembers across threads. The checkpointer is one trip's memory; the store (InMemoryStore, keyed by a namespace such as ("profiles", user_id)) is what you know about the user across trips: their car and interests. Nodes reach it through the runtime.
  • Evaluate the end state, as Anthropic recommends for agents: did intake get every field right, is the trip's feasibility right, are the stops right, does the plan pass validate? Score each agent on its own and the whole trip together; a pass overall can hide an intake agent that's right only by luck. Anthropic suggests starting with about 20 queries that represent real use.
Production reality
  • One thread per task. Reuse a thread id for a new trip and the old state comes back: the ideas list, with its append reducer, now holds last week's stops too. Generate a new thread id per trip, and keep a user id separately.
  • Approvals wait for days. People approve on Monday what the agent planned on Friday. Check that the data is still valid on resume (is the charger still available?) before acting, and expire pending approvals.
  • Checkpoints accumulate. Every step of every thread is stored. Set a retention policy, and keep personal data out of the state, or treat the checkpoint store as regulated data.
  • Memory can be wrong forever. If the intake agent misreads the car once and you store it, every future trip starts wrong. Store only what the user confirmed, show it, and let them change it.
  • Deploy without breaking running threads. A paused thread resumes with whatever code is deployed then. Keep state shapes backward compatible, or drain old threads first (Anthropic describes gradual "rainbow" deployments for exactly this).

"""End-state evaluation: judge the outcome, per agent and for the whole trip, not every intermediate turn."""
from road_trip import agents
from road_trip.network import validate
from road_trip.planning import plan_trip

FIELDS = ["origin", "destination", "vehicle_id", "start_soc", "reserve", "towing"]


def evaluate_trips(client, net, trips: list[dict]) -> dict:
    rows = []
    for t in trips:
        spec, _ = agents.intake(client, net, t["request"])
        got, want = spec.model_dump(), t["expected_spec"]
        wrong = [f for f in FIELDS if got[f] != want[f]]
        route, plan, _ = plan_trip(net, spec)
        valid = not plan.feasible or not validate(net, route, net.vehicles[spec.vehicle_id], plan,
                                                  spec.start_soc, spec.reserve, spec.towing)
        rows.append({"id": t["id"], "intake_ok": not wrong, "wrong_fields": wrong,
                     "feasible_ok": plan.feasible == t["expected"]["feasible"],
                     "stops_ok": [s.charger_id for s in plan.stops] == t["expected"]["stops"], "valid": valid})
    n = len(rows)
    return {"rows": rows, **{k: sum(r[k] for r in rows) / n for k in ("intake_ok", "feasible_ok", "stops_ok", "valid")}}

Three bugs are in graph.py, two in network.py, and one in agents.py; critic.py has none.
  1. network.py: charge_minutes uses power = charger["power_kw"], the charger's power only. A car charges at the slower of the two, so on a 350 kW charger the 100 kW Voltra City "charges" 3.5 times too fast: 20% to 80% shows as about 5 minutes instead of 18. The destination is never a charging stop, so the last leg is never checked: a plan (for example one a model edited) that reaches Harlow with 4% passes the critic, and the driver arrives nearly empty.   3. agents.py: stop_context filters the guidebook by interest (p["kind"] in interests) instead of by town, so the stop agent for Harlow receives food places from Cedar Falls, Millbrook, Elmstead and Juniper Bay. It can then suggest lunch at a diner 60 km away during a 30-minute charge, and every stop call sends more tokens than it needs.   4. graph.py: ideas is declared as a plain list[dict] with no reducer. When two stop agents run in parallel (two Send tasks in the same step), both write ideas and LangGraph raises InvalidUpdateError: At key 'ideas': Can receive only one value per step. One-stop trips work, so it slips through a quick test; every trip with two or more charging stops crashes. Give the key a reducer that merges the lists: ideas: Annotated[list[dict], operator.add].
  5. graph.py: after_critic compares state["revisions"] < MAX_REVISIONS, so the writer gets one revision instead of two: 2 writer calls, not 3, before the trip goes to needs_human. More drafts that one more rewrite would have fixed land in a person's queue. The counter counts failed reviews, so allow a rewrite while state["revisions"] <= MAX_REVISIONS (first draft + MAX_REVISIONS revisions).
  6. graph.py: approve calls booking.reserve(...) before interrupt(). def per_agent(usage: list[dict], price_in: float = 0.10, price_out: float = 0.50) -> dict:
    """Prices per 1M tokens (gpt-6-luna). Returns agent -> (calls, input, output, dollars)."""
    out: dict[str, list] = {}
    for u in usage:
        name = u["agent"].split(":")[0]                       # "stop:Harlow" -> "stop"
        row = out.setdefault(name, [0, 0, 0, 0.0])
        row[0] += 1
        row[1] += u["input_tokens"]
        row[2] += u["output_tokens"]
        row[3] += (u["input_tokens"] * price_in + u["output_tokens"] * price_out) / 1_000_000
    return {k: tuple(v) for k, v in out.items()}

Q1

When is an agentic architecture the wrong solution?

Several companies (aggregated list) · AI engineering · agents

Aggregated From a public question bank compiled from interview write-ups, Reddit threads and prep guides, with no per-question company: AI Engineering Field Guide ↗. Its prep notes name "when NOT to use agents" as a key question.

What it probes: Whether you start from the simplest thing that works, and can say with evidence when a team of agents (or any agent) costs more than it earns.

  1. Separate the options first, using Anthropic's definitions: in a workflow, code decides the path and models fill in steps; in an agent, the model picks its own steps. Start with one call, then a workflow, and use an agent only where the path can't be known in advance.
  2. Wrong when the work is deterministic: routes, battery percentages and charging minutes are functions you can test. P3's planner is code, and only three of its five roles use a model; a model doing arithmetic will eventually get it wrong in front of a customer.
  3. Wrong when the budget can't carry it: agents use about 4× the tokens of a chat and Anthropic's multi-agent system about 15×. Its 90.2% gain over a single agent came on broad research, mostly from spending more tokens in parallel.
  4. A team is wrong when the sub-tasks share context or depend on each other's decisions.   • "Agents are more flexible, so they're the better default."
  • Splitting by job title (researcher, planner, writer) because it looks like a human team, with no check that the parts are independent.

Q3

Create a system where agents collaborate to produce a research report with citations.

Several companies (aggregated list) · agentic system design · whiteboard

Aggregated A sample whiteboard problem in an interviewer-side guide to agentic system design interviews, with no company named: PromptLayer ↗; also in the AI Engineering Field Guide ↗ ("Create a system where agents collaborate on research reports with citations"). Secondary sources.

What it probes: Whether you can split the work between a coordinator and sub-agents, write the hand-offs as data, run them in parallel safely, and say what happens when one of them fails.

  1. Clarify, then justify the team: how deep, how many sources, which sources are allowed, a budget per report. Research splits well because sub-questions are independent and each needs less context than the whole; that's where Anthropic's lead agent with parallel subagents beat a single agent by 90.2%, at about 15× the tokens of a chat. Run a one-agent baseline on the same questions before claiming the team is better.
  2. Roles: a coordinator plans sub-questions and decides when there's enough; one researcher per sub-question searches and returns findings; a writer drafts; a citation check runs last. The coordinator is the only one that decides scope, so two researchers can't make conflicting implicit decisions (Cognition's mismatched Flappy Bird parts).
  3. Hand-offs as data: each researcher gets a typed task (the sub-question, what's out of scope, allowed sources, the output schema), because the prompt is the only thing a sub-agent receives. Problem 1

Cheapest route with at most k charging stops

~30 min

Your route-planning agent has a tool that returns one-way road legs between charging stations as (from, to, cost). The car can stop to charge at most k times on the way, so the route can use at most k intermediate stations (at most k + 1 legs). Return the cheapest total cost from src to dst, or -1 if no route fits.

Signature

def cheapest_route(edges: list[tuple[str, str, int]],
                   src: str, dst: str, k: int) -> int: ...

Examples

edges = [("DAL", "WAC", 30), ("WAC", "AUS", 25), ("DAL", "AUS", 80),
         ("AUS", "SAT", 20), ("WAC", "SAT", 70)]
cheapest_route(edges, "DAL", "AUS", 1)   # 55   DAL-WAC-AUS
cheapest_route(edges, "DAL", "AUS", 0)   # 80   direct leg only
cheapest_route(edges, "DAL", "SAT", 1)   # 100  DAL-WAC-SAT or DAL-AUS-SAT
cheapest_route(edges, "DAL", "SAT", 2)   # 75   DAL-WAC-AUS-SAT
cheapest_route(edges, "SAT", "DAL", 5)   # -1   legs are one-way

Constraints

  • Up to 100 stations and 10^4 legs; 0 ≤ k < number of stations; costs are non-negative integers.
  • There may be parallel legs and cycles. src == dst costs 0.

What interviewers look for: Seeing that plain Dijkstra is wrong here (the cheapest path may use too many stops), then Bellman-Ford for k + 1 rounds, relaxing from a copy of the previous round. A Dijkstra variant on (cost, station, stops) is also accepted if you explain the pruning.

Check: (1) All five calls in the example. (2) With legs A-B, B-C, C-D, D-E (1 each) and A-X, X-E (10 each): k=3 gives 4, k=1 gives 20. (3) With legs ("A","B",1), ("B","C",1), ("A","C",5) and k=0 the answer is 5, not 2. If you get 2, your round chains two legs.

Let cost[v] be the cheapest way to reach v with at most r legs. Round r + 1: for every leg (u, v, c), try cost[u] + c. Run k + 1 rounds. The trap: if you update cost in place, one round can chain several legs and break the stop limit. Read from the previous round's costs and write into a copy.

import math


def cheapest_route(edges: list[tuple[str, str, int]], src: str, dst: str, k: int) -> int:
    """Cheapest cost from src to dst using at most k charging stops
    (intermediate stations), so at most k + 1 legs. Edges are directed
    (from, to, cost) with cost >= 0. Return -1 if no such route exists.

    Bellman-Ford limited to k + 1 rounds. Each round relaxes from a copy of
    the previous round's costs, so one round adds at most one leg.

    Complexity: O((k + 1) * E) time, O(V) space.
    """
    if src == dst:
        return 0
    if k < 0:
        return -1
    cost = {src: 0}
    for _ in range(k + 1):
        nxt = dict(cost)
        for u, v, c in edges:
            if u in cost and cost[u] + c < nxt.get(v, math.inf):
                nxt[v] = cost[u] + c
        cost = nxt
    return cost.get(dst, -1)

Complexity: O((k + 1) · E) time, O(V) space.

Problem 2

Schedule agent tasks in parallel waves

~30 min

An orchestrator gets a plan of sub-agent tasks. Each task lists the tasks whose results it needs. You want to run as much as possible in parallel: first every task with no dependencies, then every task whose dependencies are all done, and so on. Each group is a wave.

Return the waves in order, each wave sorted by task name. Raise ValueError if the plan has a cycle (it can never finish) or names a dependency that isn't a task.

Signature

def schedule_waves(tasks: dict[str, list[str]]) -> list[list[str]]: ...

Examples

schedule_waves({
    "fetch_lead": [], "fetch_rate": [], "fetch_notes": [],
    "compute_dti": ["fetch_lead", "fetch_rate"],
    "summarize": ["fetch_notes"],
    "assess": ["compute_dti", "summarize"],
})
# [["fetch_lead", "fetch_notes", "fetch_rate"], ["compute_dti", "summarize"], ["assess"]]

schedule_waves({"a": ["c"], "b": ["a"], "c": ["b"]})   # raises ValueError (cycle)

Constraints

  • Up to 10^4 tasks and 10^5 dependency edges. A dependency may be listed twice.
  • A task that depends on itself is a cycle.

What interviewers look for: Kahn's algorithm processed level by level, with in-degree counts and a reverse map from each task to its dependents. Cycle detection by counting scheduled tasks. Bonus: say what the waves mean for latency (total time is the sum of the slowest task per wave).

Check: (1) The example plan gives three waves as shown. (2) {"a": [], "b": ["a"], "c": ["a", "b"]} → [["a"], ["b"], ["c"]]: c waits for its slowest dependency. (3) {"a": ["a"]} and {"a": ["ghost"]} both raise ValueError.

Count each task's unmet dependencies (its in-degree) and build the reverse map: dependency → tasks that wait for it. Wave 0 is every task with in-degree 0. To build the next wave, go through the current wave and decrement each dependent; those that reach 0 form the next wave. If the waves hold fewer tasks than the plan, the rest are stuck in a cycle. Use set(deps) so a repeated dependency counts once.

def schedule_waves(tasks: dict[str, list[str]]) -> list[list[str]]:
    """Group tasks into waves that can run in parallel. tasks maps each task
    to the tasks it depends on. Wave 0 holds tasks with no dependencies;
    each later wave holds tasks whose dependencies are all in earlier waves.
    Each wave is sorted. Raise ValueError on a cycle or an unknown
    dependency.

    Kahn's algorithm, processed one level at a time.

    Complexity: O(V + E + V log V) time (the log factor is sorting each
    wave), O(V + E) space.
    """
    indegree = {t: 0 for t in tasks}
    dependents: dict[str, list[str]] = {t: [] for t in tasks}
    for task, deps in tasks.items():
        for dep in set(deps):
            if dep not in tasks:
                raise ValueError(f"unknown dependency {dep!r} of {task!r}")
            indegree[task] += 1
            dependents[dep].append(task)

    wave = sorted(t for t, d in indegree.items() if d == 0)
    waves = []
    done = 0
    while wave:
        waves.append(wave)
        done += len(wave)
        nxt = []
        for t in wave:
            for child in dependents[t]:
                indegree[child] -= 1
                if indegree[child] == 0:
                    nxt.append(child)
        wave = sorted(nxt)
    if done != len(tasks):
        raise ValueError("dependency cycle")
    return waves

Complexity: O(V + E) time plus O(V log V) for sorting the waves; O(V + E) space.
