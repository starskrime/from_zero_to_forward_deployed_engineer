2. Which Python are you running?

$ python3 --version
Python 3.13.x        # 3.11 or newer is fine
$ which python3        # Windows: where python
If your prompt starts with (base)Anaconda is active and will interfere with virtual environments. Run conda deactivate, and to stop it starting automatically, conda config --set auto_activate_base false once. If your Python is older than 3.11, install the latest from python.org.

3. Virtual environments: one isolated toolbox per project

The problem: if every package goes into one shared Python, projects start to conflict. One project needs one version of a library, another needs a different one, and nobody else can reproduce your setup.

The fix: each project gets its own .venv folder with its own Python and packages. "Activating" it tells your terminal to use that folder's python and pip.

$ python3 -m venv .venv            # create: once per project
$ source .venv/bin/activate        # activate: every new terminal (Windows: .venv\Scripts\activate)
(.venv) $ which python                # proof: points inside .venv
(.venv) $ pip install rich
(.venv) $ pip freeze > requirements.txt  # record exact versions
(.venv) $ deactivate

To rebuild the environment elsewhere: create and activate a new .venv, then pip install -r requirements.txt.

4. VS Code, set up properly

  1. Install the Python extension from Microsoft.
  2. Enable the code command: ⌘⇧P → "Shell Command: Install 'code' command in PATH". Now code . opens the current folder.
  3. ⌘⇧P → "Python: Select Interpreter" → choose the one inside .venv.
  4. Open the built-in terminal with ⌃`. It activates the selected environment automatically.
Production reality
  • Virtual environments don't survive a move. activate and the first line of .venv/bin/pip contain the folder's absolute path. After you rename or move a project, pip fails because that path no longer exists ("bad interpreter" on macOS), and which python quietly points back at the system Python. Delete .venv and rebuild it from requirements.txt. Never copy a venv to another machine or commit it.
  • pip uninstall leaves orphans. Uninstalling rich leaves markdown-it-py, mdurl and Pygments installed, and the next pip freeze pins them into requirements.txt. When your dependencies change, rebuild the venv from scratch and freeze again. A requirements file full of packages nobody imports is the first thing a reviewer notices.
  • Use python -m pip. A bare pip is whichever pip comes first on your PATH, and it may belong to a different Python. python -m pip install … always installs into the interpreter you'll actually run. Most "I installed it but still get ModuleNotFoundError" problems are this.
  • System Pythons now refuse pip. Recent Homebrew and Linux-distribution Pythons stop pip install outside a venv with error: externally-managed-environment (PEP 668). Don't use --break-system-packages; create a venv.
  • requirements.txt doesn't record your Python version. Code with dict | None annotations runs on 3.10 and later but fails at import on 3.9. Put the minimum version in the README (this program uses 3.11+), and when a teammate's setup fails, ask for python3 --version first.

Core · Packages and git

1. Module, package, import

  • A module is one .py file. text.py is the module text.
  • A package is a folder of modules with an __init__.py (it can be empty).
  • Imports follow folders with dots: from greeter.text import shout means "open greeter/text.py and take shout".
import csv                          # whole module; use as csv.DictReader
from pathlib import Path            # one name from a module
from greeter.text import shout      # your own package, same syntax

2. __name__ and if __name__ == "__main__":

Python sets __name__ in every file. If you run the file, it's "__main__"; if another file imports it, it's the module's name (like "greeter.text"). The if check lets one file be both a reusable library and a runnable script.

def shout(name: str) -> str:
    return f"HELLO, {name.upper()}!"

if __name__ == "__main__":
    print(shout("test"))   # runs with: python -m greeter.text, NOT when imported

3. __main__.py and python -m

Put a __main__.py inside a package, and python -m greeter runs it. Always run from the project root, the folder that contains the package.

4. The project layout you'll use all program

lead-intake/                 ← project root: run commands from here
├── .venv/                   ← ignored by git

├── .gitignore

├── README.md
├── data/leads_sample.csv

Keeping input/output, business rules and the command line separate is exactly the habit hiring managers look for, and it's what makes code testable (next week).

.venv/

*.pyc

Secrets rule, from now onBefore every first commit, run git status and confirm .env isn't listed. If a key ever reaches GitHub, revoke it immediately. Deleting the file afterwards doesn't remove it from history.
Production reality
  • Running by path and running with -m are different. python greeter/__main__.py puts greeter/ on the import path, so from greeter.text import … fails with ModuleNotFoundError. python -m greeter from the project root puts the root there. Scheduled jobs and CI configs should cd to the project root and use -m.
  • Don't name files after the standard library. A csv.py, json.py or logging.py in your folder is imported instead of the real module, and you get AttributeError: module 'csv' has no attribute 'DictReader'. Scratch files named after what you're learning are the usual culprit.
  • .gitignore only affects untracked files. If .env was committed once, git add . keeps staging every change to it. Run git rm --cached .env and commit. git check-ignore -v .env prints the .gitignore line that matches, and git ls-files shows what's still tracked.
  • A pushed secret is a leaked secret. Automated scanners watch public repositories, and every clone and fork keeps its own copy of the history. Revoke the key first, then clean up. Rewriting history (for example with git filter-repo) is housekeeping, not the fix.
  • Write .gitignore before your first git add . A fresh venv holds about 1,900 files (Python 3.11, pip only), so committing it by mistake buries your real changes and bloats the repository for good. If it happens, run git rm -r --cached .venv, add it to .gitignore, and commit.

Three data-wrangling functions

~45 min

In code/week-0A/drills/tue_drills.py, write and test these (you'll use all three patterns this weekend):

  1. unique_emails(emails): remove duplicates ignoring case and surrounding spaces, keep first-seen order, return lowercase.
  2. leads_per_state(states): count per state (uppercased), return a list of (state, count), most common first, ties alphabetical.
  3. ids_by_loan_type(rows): given dicts with lead_id and loan_type, return {loan_type: [ids…]}.
assert unique_emails(["A@x.com", "b@x.com", " a@X.com "]) == ["a@x.com", "b@x.com"]
assert leads_per_state(["TX", "ca", "TX", "CA", "ny"]) == [("CA", 2), ("TX", 2), ("NY", 1)]
A set answers "have I seen this?" quickly. collections.Counter counts. dict.setdefault(key, []) creates a list the first time a key appears. Sort with a key of (-count, name).
from collections import Counter


def unique_emails(emails: list[str]) -> list[str]:
    seen, out = set(), []
    for e in emails:
        key = e.strip().lower()
        if key not in seen:
            seen.add(key)
            out.append(key)
    return out


def leads_per_state(states: list[str]) -> list[tuple[str, int]]:
    counts = Counter(s.strip().upper() for s in states)
    return sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))


def ids_by_loan_type(rows: list[dict]) -> dict[str, list[str]]:
    groups: dict[str, list[str]] = {}
    for r in rows:
        groups.setdefault(r["loan_type"], []).append(r["lead_id"])
    return groups

Core · Files and bad data

1. Paths with pathlib

from pathlib import Path

HERE = Path(__file__).parent                 # the folder this .py file lives in
INPUT = HERE / "data" / "leads_sample.csv"    # "/" joins path parts
OUT_DIR = Path("out")
OUT_DIR.mkdir(parents=True, exist_ok=True)   # create if missing; no error if it exists

2. Reading CSV: every value is a string

import csv

with INPUT.open(newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f):     # each row is a dict keyed by the header
        print(row["credit_score"])    # '742'  ← a str, not an int!
  • Every value is text. An empty cell is "", not None.
  • newline="" is required by the csv docs; encoding="utf-8" handles names like "Müller".
  • Number rows the way a person sees the file: the header is line 1, so use enumerate(reader, start=2).

3. Converting text safely

int("742")                        # 742
int("")                           # ValueError
int("7.5")                        # ValueError: use float()
float("three")                    # ValueError
from datetime import date
date.fromisoformat("2026-09-31")  # ValueError: September has 30 days

A value can convert fine and still be wrong, like a credit score of 905. That's a range check, and you write it yourself.

4. Exceptions: catch, record, continue

def parse_credit_score(raw: str) -> int:
    if raw.strip() == "":
        raise ValueError("credit_score is missing")
    score = int(raw)
    if not 300 <= score <= 850:
        raise ValueError(f"credit_score {score} is outside 300-850")
    return score

try:
    score = parse_credit_score(row["credit_score"])
except ValueError as e:              # catch the SPECIFIC error, never a bare except:
    errors.append(str(e))            # record it, and the loop continues
The data-pipeline mindsetOne bad row must never crash the run. Validate each row, collect errors with enough context to fix them (row, ID, field, reason), and keep going. Stop only when the whole run is meaningless, like a missing input file. The same pattern returns when agent tools fail.

5. Writing JSON

import json
with (OUT_DIR / "summary.json").open("w", encoding="utf-8") as f:
    json.dump(summary, f, indent=2)

JSON stores dicts, lists, strings, numbers, booleans and null, but not date objects or sets. Convert with d.isoformat() and sorted(s).

Production reality
  • Excel adds an invisible character. Files saved as "CSV UTF-8" start with a byte order mark, so the first header becomes '\ufefflead_id' and row["lead_id"] raises KeyError. .strip() doesn't remove it. Open customer files with encoding="utf-8-sig", which also reads files without the mark.
  • Ragged rows don't raise errors. A row with too few fields gets None (not "") for the missing ones, and None.strip() crashes with AttributeError, which your except ValueError doesn't catch. Extra fields are stored under the key None. Check the field count and report bad rows as errors: a cut-off export is the most common case.
  • Row numbers drift on multi-line cells. A quoted cell containing a line break (a notes field, say) takes two lines in the file, so enumerate(reader, start=2) no longer matches the line a person sees. reader.line_num gives the actual line in the file; report that when files can contain free text.
  • A failed json.dump leaves a broken file. open("w") empties the file immediately and json.dump writes piece by piece, so an unsupported value halfway through leaves {"total_rows": 20, "run_date": on disk for the next job to choke on. Write to a temporary file and Path.replace() it into place, or build the text with json.dumps first.
  • NaN slips through range checks. float("nan") works, and every comparison with NaN is False, so if value < 0: raise lets it through. json.dump then writes NaN, which is not valid JSON, and JavaScript's JSON.parse rejects it. Check math.isfinite(value), and pass allow_nan=False when downstream systems parse your JSON.

import csv
import json
from pathlib import Path

HERE = Path(__file__).parent
INPUT = HERE / "data" / "leads_sample.csv"
OUTPUT = HERE / "out" / "summary.json"


def parse_credit_score(raw: str) -> int:
    if raw.strip() == "":
        raise ValueError("credit_score is missing")
    score = int(raw)
    if not 300 <= score <= 850:
        raise ValueError(f"credit_score {score} is outside 300-850")
    return score


def main() -> None:
    total, scores, errors = 0, [], []
    with INPUT.open(newline="", encoding="utf-8") as f:
        for row_number, row in enumerate(csv.DictReader(f), start=2):
            total += 1
            try:
                scores.append(parse_credit_score(row["credit_score"]))
            except ValueError as e:
                errors.append({"row": row_number, "lead_id": row["lead_id"], "error": str(e)})

    summary = {
        "total_rows": total,
        "valid_scores": len(scores),
        "average_score": round(sum(scores) / len(scores), 1) if scores else None,
        "errors": errors,
    }
    OUTPUT.parent.mkdir(parents=True, exist_ok=True)
    with OUTPUT.open("w", encoding="utf-8") as f:
        json.dump(summary, f, indent=2)
    print(f"Wrote {OUTPUT} ({len(errors)} errors)")


if __name__ == "__main__":
    main()

Real exports are messy

~45 min

In code/week-0A/drills/wed_drills.py:

Clean first (strip, remove $ and commas), then convert. For dates, try one format; if it raises ValueError, try the next with datetime.strptime(raw, "%m/%d/%Y"); if both fail, raise your own clear error.
from datetime import date, datetime


def parse_amount(raw: str) -> float:
    cleaned = raw.strip().replace("$", "").replace(",", "")
    if cleaned == "":
        raise ValueError("amount is missing")
    return float(cleaned)


def parse_date(raw: str) -> str:
    raw = raw.strip()
    try:                                     # note: on Python 3.11+ this also accepts 20260901 and 2026-W36-2;
        return date.fromisoformat(raw).isoformat()   # the weekend rule is strictly YYYY-MM-DD, so check the shape first there
    except ValueError:
        pass
    try:
        return datetime.strptime(raw, "%m/%d/%Y").date().isoformat()
    except ValueError:
        raise ValueError(f"unrecognized date: {raw!r}") from None

Production reality
  • Real environment variables beat .env. load_dotenv() only sets variables that aren't already set, so a stale export LOG_LEVEL=WARNING in your terminal, or a CI setting, silently wins. And every value is a string: DRY_RUN=false is truthy, and MAX_ROWS=100 is "100". Parse booleans and numbers explicitly, with defaults.
  • Logs go to stderr. logging.basicConfig writes to stderr, so > run.log captures nothing from logging. Use 2> run.log, or > run.log 2>&1 for both streams. Keep stdout for real output (data another program reads) and logs for people and log collectors.
  • Know the exit codes. sys.exit(None) and a bare return from main() both exit 0. sys.exit("message") prints the message to stderr and exits 1. An uncaught exception exits 1. argparse exits 2 on bad arguments. Codes run from 0 to 255, so sys.exit(256) exits 0. Return explicit ints from main().
  • Pipes hide failures. In python -m lead_intake in.csv | tee run.log, the pipeline's exit code is tee's (0), even under set -e, and the next step runs on stale output. Add set -o pipefail to every shell script that runs your tools.
  • basicConfig works only once. If the root logger already has a handler (from an earlier basicConfig call, or a library that configured logging), later calls do nothing, and your level and format are ignored. Configure logging once, at the start of main(), or pass force=True.

import sys

def parse_args(argv=None) -> argparse.Namespace:

                                     description="Validate a CSV of mortgage leads and write a JSON report.")

def main(argv=None) -> int:
    setup_logging()
    args = parse_args(argv)
    logger.debug("Arguments: %s", args)
    if not args.input.exists():
        logger.error("Input file not found: %s", args.input)
        return 1
    logger.info("Would process %s into %s", args.input, args.output_dir)
    return 0

~60 min

Download ⬇ lead-intake-drill.zip, unzip it, read its README, and run the tests. The code runs, but six tests fail. Each failure is a mistake that shows up in real projects. Check: all 9 tests pass, offline. Then explain each bug out loud in one sentence, as you would to an interviewer who asks "how would this fail in production?"

Read each failing test's name and assertion before opening the code. The bugs are in rules.py, parsing.py, validation.py, pipeline.py, report.py, cli.py.
  1. rules.py: STATES_FILE = Path("lead_intake") / "us_states.txt" is resolved against the current working folder, not the package. It works when you run from the project root and crashes with FileNotFoundError (at import time) when cron, CI or a teammate runs the tool from anywhere else. Build the path from the code's own location: Path(__file__).parent / "us_states.txt".
  2. parsing.py: the hand-written calendar gives every month except April, June, September and November 31 days, so 2026-02-30 and 2026-02-29 pass and land in the CRM as dates that don't exist (the sample's 2026-09-31 is still caught, which is why the bug survives a quick check). Let the standard library decide: date(year, month, day) raises ValueError for impossible dates, leap years included.
  3. validation.py: property_state is upper-cased but not stripped, so " tx " becomes "TX ", fails the state lookup and a good lead is rejected. Every other field strips; this one was missed. Use .strip().upper().
  4. pipeline.py: the dict comprehension meant to record where each lead_id first appears keeps the last row for each key (later assignments overwrite earlier ones). The report still says 1 duplicate, but it rejects row 8, the original L-1007, and accepts the later copy on row 16, so the web team is told to fix the wrong row. Record the first row with setdefault in a loop.
  5. report.py: the tally starts a new field at 1 and then adds 1 again, so every field's first error is counted twice: errors_by_field shows loan_amount 4, credit_score 3 and 2 for everything else, while the totals (20 / 9 / 11) still look right. Start the count at 0 (or use counts.get(field, 0) + 1 or collections.Counter).
  6. cli.py: a bare return after the "Input file not found" error returns None, and sys.exit(None) exits with code 0. The log says ERROR, but the nightly job, CI and any script checking $? see success and carry on with no data. Return 1.

Q1

Find and fix a double-counting bug in a function that tallies values in a HashMap.

Palantir · Forward Deployed Software Engineer · re-engineering

Reported Prep-site guide: Exponent ↗. The round's format (about 60 minutes reading unfamiliar code, finding why hidden tests fail, requirements that change mid-round) is described in a prep write-up: Coditioning ↗. Secondary sources; not an official question.

What it probes: Whether you can read code you didn't write, reproduce a bug with a tiny input, and fix the cause instead of the symptom, while explaining your thinking.

  1. Pin down the contract before touching code: what should each count mean (occurrences, rows, distinct keys), and what should empty input return?
  2. Reproduce with the smallest failing input and write it as a test first, for example ["a", "a", "b"] should give {"a": 2, "b": 1}.
  3. Read the tally for the usual causes: a new key initialized to 1 and then incremented, the same count made in two places (a helper and its caller), or two partial maps merged by adding keys that overlap.
  4. Fix the cause with an idiom whose behavior is obvious (counts.get(k, 0) + 1 or collections.Counter), and walk through the first-occurrence, repeat and empty cases out loud.
  5. Run the whole test suite, not just your new test, and add an invariant check: the counts must sum to the number of items tallied.
  6. Talk while you work. In this format, how you narrow the problem down counts as much as the fix.

Answers that fail:

  • Rewriting the function from scratch before understanding why it's wrong.
  • Patching the output (halving counts, subtracting 1) instead of fixing where the count is made.
  • Ten silent minutes of print debugging with no hypothesis stated.

Q3

File deduplication.

Anthropic · Forward Deployed Engineer · coding (CodeSignal)

Reported Named as a coding problem in a prep-site guide: Exponent ↗. The guide gives only the problem's name. Practice this version: given a folder, find the groups of files whose contents are identical. Secondary source.

What it probes: pathlib and file handling at realistic scale, choosing cheap checks before expensive ones, and handling errors without crashing.

  1. Clarify: identical content or identical names? Include hidden files? Follow symbolic links? How big are the largest files? What should the output look like?
  2. Walk the tree with Path.rglob("*"), keep regular files only, and group by size first: files of different sizes can't be identical, so most files are ruled out without being read.
  3. Hash only same-size candidates, reading in chunks (for example hashlib.sha256 over 1 MB blocks) so a 10 GB file doesn't fill memory. Optionally hash the first block first, then compare bytes to confirm matches.
  4. Handle PermissionError and files that disappear mid-scan by recording them and continuing (this week's catch, record, continue).
  5. Return groups in a stable, sorted order and test with tmp_path: empty files, one file, two identical files with different names.
  6. Keep scanning, grouping and reporting in separate functions, so a later stage ("now delete duplicates, keeping the oldest") is a small addition.

Answers that fail:

  • Reading every file fully into memory, or hashing everything before grouping by size.
  • Comparing every pair of files: O(n²) full reads.
  • Crashing on the first unreadable file.
Q4

Implement an LRU cache, then extend it across stages.

Anthropic · Forward Deployed Engineer · coding (CodeSignal)

Reported Prep-site guide: Exponent ↗ ("LRU cache extended across stages"). The stages themselves aren't public, so the extensions below are examples. Secondary source.

What it probes: Command of dicts and ordering, O(1) operations, and whether your first version is clean enough to extend under time pressure.

  1. Clarify the interface (get(key), put(key, value)), the capacity, what a miss returns, and whether a get counts as a use.
  2. Use collections.OrderedDict: move_to_end(key) on every use and popitem(last=False) to evict the least recently used entry, all O(1). A plain dict also keeps insertion order, so popping and reinserting a key works too.
  3. Write the eviction-order test first: capacity 2, put a, put b, get a, put c, and b must be gone.
  4. Typical extensions: expiry times, capacity by total size instead of count, hit and miss statistics, thread safety with a lock. Each is small if the core stays small.
  5. Say why functools.lru_cache doesn't fit here: it memoizes a function's results and doesn't give you explicit put, get or eviction control.

Answers that fail:

  • Tracking recency in a list, which makes every get O(n).
  • Never testing which key gets evicted.
  • Rewriting everything at each stage because the first version wasn't structured.
