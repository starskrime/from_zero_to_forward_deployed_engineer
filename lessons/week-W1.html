Read the overview and the first full example. You'll implement exactly this today.

Summary

  • Workflow: your code decides the steps; the model fills in each one (for example extract, then classify, then draft). Predictable, cheap, easy to test.
  • Agent: the model decides the next step from what it has seen so far, in a loop, until it's done. Flexible, but less predictable and more expensive.
  • Start with the simplest thing that works. Use an agent only when the steps can't be known ahead of time. Many "agents" in production are workflows with one smart step.
  • The agent equation: instructions + tools + memory, run by a model, inside a loop you control (with a step limit, logging and cost tracking).
  • Function calling: you describe tools as JSON schemas. The model never runs anything. It replies with a function_call (a name and JSON arguments); your code runs the function and sends back a function_call_output with the same call_id. Then the model continues.
  • Why tools matter: they give the model fresh data (databases, APIs) and exact computation (math, dates), which is exactly where Week 0C showed models are weakest.
Production reality
  • Every step re-sends everything. The API is stateless, so each request carries the instructions, the tool definitions and every earlier call and result. A run that starts at 2,000 input tokens and grows by 400 per step bills 18,000 input tokens over 6 requests, not the 4,400 you get by counting only new items. Put step counts in your cost estimates, and keep tool results small.
  • Tool definitions cost tokens on every request. Twenty tools with 150-token descriptions add 3,000 input tokens to each request, or 24,000 over an 8-step run, before any work is done. Send only the tools a task needs, and merge tools that are always called together.
  • Units are where tool calls go wrong. Strict mode guarantees that annual_rate_pct is a number, not that it's 6.25 rather than 0.0625. The fraction gives a $1,135.61 payment instead of $2,493.65 on Nadia Aliyeva's loan, and a DTI of 13.9% instead of 26.7%. Put the unit and an example in every numeric description, and have the tool reject implausible values (a mortgage rate below 1% is almost certainly a fraction).
  • Latency grows with steps. Each tool step is a full model round trip, so a 5-request agent takes several times as long as a 1-call workflow on the same model. For batch jobs this is cost and throughput; for a user waiting on a screen, show progress from the trace and stream the final answer.
  • tool_choice applies to each request you send it on. "required" forces a call in every reply, so a loop that always sends it can never finish and every run ends at max_steps. If you must force the first call, send "required" (or a named function) on the first request only, then "auto".

Core · Tools a model can use well, and output your code can trust

Read
Anthropic: Writing effective tools for agents ↗

How to name, describe and shape tools, and what to return from them.

Read
OpenAI: Structured model outputs ↗

Read the Pydantic example and the section on refusals.

Summary

  • Strict mode ("strict": true) makes arguments always match your schema. Its rules: additionalProperties: false on every object, and every property listed in required. An optional field is written as a type that allows null.
  • Descriptions are prompts. Name tools and parameters clearly, give units and examples ("annual rate in percent, e.g. 6.5"), and use enum for fixed choices. The test: could a new colleague use the tool from its description alone?
  • Keep the tool set small (OpenAI suggests fewer than 20 at a time), and merge tools that are always called together.
  • Return errors as data ({"error": "no lead with id L-9999"}) instead of crashing, so the model can recover or explain.
  • Structured output: client.responses.parse(..., text_format=MyModel) makes the model reply in your Pydantic model's shape; read it from response.output_parsed. It's None if the model refused, so check before using it.
  • Tools vs structured output: use tools when the model needs to act or fetch; use structured output when you need its final answer in a shape your code can store.
  • The schema checks shape, not business rules. Add Pydantic validators for rules like "a hot lead must score 8–10".
Production reality
  • Defaults don't make fields optional. responses.parse turns your Pydantic model into a strict schema that lists every field in required, including fields with defaults, so the model always writes a value and your default never applies. For "may be missing", use X | None and decide in code what None means.
  • Truncation isn't a refusal. When the model hits max_output_tokens in the middle of the JSON, responses.parse raises a pydantic ValidationError (type json_invalid); output_parsed is None only for refusals. Reasoning tokens count toward the same limit, so leave headroom, and catch ValidationError for each item in a batch.
  • A valid schema can still hold wrong numbers. Structured output guarantees shape, not truth: a LeadScore can report a 26.7% DTI when the tool returned 46.2%. Before storing, check that monthly_payment and dti_pct equal values in the trace, and reject the assessment if they don't.
  • Errors-as-data can hide your own bugs. A dispatcher that catches TypeError also catches "argument after ** must be a mapping, not str" from a forgotten json.loads, and hands it to the model, which retries until max_steps. Log every error result by tool, alert when a tool's error rate jumps, and unit-test run() directly.
  • Validators fail after you've paid. When a model_validator rejects the output, the tokens are spent and you have nothing to store. Send the validator's message back once and parse again, record how often that happens, and treat a rising rate as a prompt or model problem, not noise.

In Pydantic, str | None with no default becomes "required but nullable" in the schema, which is exactly what strict mode wants. Literal[...] | None gives an enum that also allows null.
from typing import Literal

from openai import OpenAI
from pydantic import BaseModel


class LeadIntake(BaseModel):
    full_name: str | None
    email: str | None
    loan_amount: float | None
    loan_type: Literal["purchase", "refinance"] | None
    property_state: str | None
    credit_score: int | None
    missing_fields: list[str]


INSTRUCTIONS = ("Extract the mortgage lead from the broker's email. Use null for anything not stated; "
                "never guess. property_state is a two-letter US code. List the null fields in missing_fields.")


def extract(client: OpenAI, email_text: str) -> LeadIntake:
    response = client.responses.parse(model="gpt-6-luna", instructions=INSTRUCTIONS,
                                      input=email_text, text_format=LeadIntake)
    if response.output_parsed is None:
        raise ValueError("no structured output (the model may have refused)")
    return response.output_parsed

Core · Turning one tool call into an agent

The loop in six lines

repeat up to max_steps:
    response = model(conversation, tools)
    conversation += response.output            # includes reasoning items: send them back
    calls = function calls in response.output
    if no calls: return response.output_text   # the model is done
    for each call: run it, append its function_call_output
  • The stopping condition is "the model asked for no tools", never a keyword in the text.
  • A step limit is your safety net against loops that never end (and bills that never stop).
  • Parallel calls: one response can contain several function calls. Run them all, then call the model once.
  • A dispatcher maps tool names to Python functions, rejects unknown names, and turns exceptions into {"error": ...} results.
  • A trace (each tool, its arguments and its result) is how you debug an agent. Print it now; next week you'll store it.
  • Track tokens and cost across every call in the loop: an agent makes several calls per task.
  • Short-term memory is simply the conversation list. Keep it between questions and the agent can answer follow-ups.
Production reality
  • Single-call loops break on parallel calls. Parallel calls are on by default. A loop that answers only the first call sends a request with an unanswered call, and the API rejects it with a 400; the same rule holds on Claude (a tool_result for every tool_use). If tools depend on each other's results or have side effects, set parallel_tool_calls=False instead of hoping the model calls them one at a time.
  • The SDK retries under your loop. openai-python and anthropic-python retry failed requests twice by default (connection errors, 408, 409, 429 and 5xx), and the default read timeout is 600 seconds. One stuck request can hold an 8-step run for many minutes; set timeout= (and max_retries=) on the client for batch jobs, and log retries so slow runs are explainable.
  • Set max_steps from real traces. Count requests per run on real data, set the limit at roughly twice the typical count, and track how many runs hit it each day. A sudden rise almost always means a tool started returning errors that the model keeps retrying.
  • Big tool results stay in every later request. A list_leads tool that returns 5,000 rows at about 25 tokens each adds 125,000 tokens, re-sent on every following step. Return only the fields the model needs, cap the rows, and say so in the result ("showing 20 of 5,000; filter by state").
  • Side-effect tools need guards. A model can call the same tool twice (in parallel, or after a retry), and text in tool results can steer which tools it calls. Give tools that write or send an idempotency key, check names against an allow-list before dispatch, and move irreversible actions out of the agent into code that a person approves.

def run(self, name: str, arguments: str) -> str:
    if name not in {t["name"] for t in TOOLS}:
        return json.dumps({"error": f"unknown tool {name}"})
    try:
        return json.dumps(getattr(self, name)(**json.loads(arguments)))
    except (LookupError, ValueError, TypeError) as e:
        return json.dumps({"error": str(e)})
import json
import sqlite3

from openai import OpenAI


def tool(name, description, properties):
    return {"type": "function", "name": name, "description": description, "strict": True,
            "parameters": {"type": "object", "properties": properties,
                           "required": list(properties), "additionalProperties": False}}


TOOLS = [
    tool("list_leads_by_state", "List leads in a US state: lead_id, full_name, loan_amount, loan_type.",
         {"state": {"type": "string", "description": "Two-letter code, e.g. TX"}}),
    tool("get_lead", "Get one lead's full record.", {"lead_id": {"type": "string"}}),
    tool("calculate_payment", "Monthly principal-and-interest payment for a fixed-rate loan.",
         {"principal": {"type": "number"}, "annual_rate_pct": {"type": "number"}, "years": {"type": "integer"}}),
]


class LeadTools:
    def __init__(self, conn: sqlite3.Connection):
        self.conn = conn

    def list_leads_by_state(self, state: str) -> list[dict]:
        rows = self.conn.execute("SELECT lead_id, full_name, loan_amount, loan_type FROM leads "
                                 "WHERE property_state = ?", (state.upper(),)).fetchall()
        return [dict(zip(["lead_id", "full_name", "loan_amount", "loan_type"], r)) for r in rows]

    def get_lead(self, lead_id: str) -> dict:
        cur = self.conn.cursor()
        cur.row_factory = sqlite3.Row                 # dict-like rows, for this query only
        row = cur.execute("SELECT * FROM leads WHERE lead_id = ?", (lead_id,)).fetchone()
        if row is None:
            raise LookupError(f"no lead {lead_id}")
        return dict(row)

    def calculate_payment(self, principal: float, annual_rate_pct: float, years: int) -> dict:
        r, n = annual_rate_pct / 100 / 12, years * 12
        return {"monthly_payment": round(principal * r / (1 - (1 + r) ** -n), 2)}

    def run(self, name: str, arguments: str) -> str:
        if name not in {t["name"] for t in TOOLS}:
            return json.dumps({"error": f"unknown tool {name}"})
        try:
            return json.dumps(getattr(self, name)(**json.loads(arguments)))
        except (LookupError, ValueError, TypeError) as e:
            return json.dumps({"error": str(e)})


def run_agent(client, tools: LeadTools, conversation: list, max_steps: int = 6) -> str:
    for step in range(1, max_steps + 1):
        response = client.responses.create(
            model="gpt-6-luna", input=conversation, tools=TOOLS,
            instructions="Answer questions about mortgage leads. Use tools for data and math.")
        conversation += response.output
        calls = [i for i in response.output if i.type == "function_call"]
        if not calls:
            return response.output_text
        for call in calls:
            result = tools.run(call.name, call.arguments)
            print(f"step {step}: {call.name}({call.arguments}) -> {result[:100]}")
            conversation.append({"type": "function_call_output", "call_id": call.call_id, "output": result})
    raise RuntimeError(f"no answer after {max_steps} steps")


if __name__ == "__main__":
    from dotenv import load_dotenv
    load_dotenv()
    client, tools = OpenAI(), LeadTools(sqlite3.connect("out/crm.db"))
    conversation = []                                 # short-term memory, kept across questions
    while (question := input("\nYou: ").strip()) not in {"", "quit"}:
        conversation.append({"role": "user", "content": question})
        print("Agent:", run_agent(client, tools, conversation))

import json

import anthropic

from agent import TOOLS, LeadTools

CLAUDE_TOOLS = [{"name": t["name"], "description": t["description"], "input_schema": t["parameters"]}
                for t in TOOLS]


def run_claude(client: anthropic.Anthropic, tools: LeadTools, question: str, max_steps: int = 6) -> str:
    messages = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        msg = client.messages.create(model="claude-haiku-4-5", max_tokens=1024,
                                     tools=CLAUDE_TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": msg.content})
        if msg.stop_reason != "tool_use":
            return "".join(b.text for b in msg.content if b.type == "text")
        results = []
        for block in msg.content:
            if block.type == "tool_use":
                output = tools.run(block.name, json.dumps(block.input))
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": output,
                                "is_error": '"error"' in output})
        messages.append({"role": "user", "content": results})
    raise RuntimeError("no answer")

import Anthropic from "@anthropic-ai/sdk";

function calculatePayment(principal: number, annualRatePct: number, years: number): number {
  const r = annualRatePct / 100 / 12;
  const n = years * 12;
  return Math.round((principal * r) / (1 - (1 + r) ** -n) * 100) / 100;
}

const tools: Anthropic.Tool[] = [{

  input_schema: {
    type: "object",
    properties: { principal: { type: "number" }, annual_rate_pct: { type: "number" }, years: { type: "integer" } },
    required: ["principal", "annual_rate_pct", "years"],
  },
}];

type PaymentInput = { principal: number; annual_rate_pct: number; years: number };

export async function ask(client: Anthropic, question: string, maxSteps = 5): Promise<string> {
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: question }];
  for (let step = 0; step < maxSteps; step++) {
    const response = await client.messages.create({ model: "claude-haiku-4-5", max_tokens: 1024, tools, messages });
    messages.push({ role: "assistant", content: response.content });
    if (response.stop_reason !== "tool_use") {
      return response.content.filter((b): b is Anthropic.TextBlock => b.type === "text").map(b => b.text).join("");
    }
    const results: Anthropic.ToolResultBlockParam[] = [];
    for (const block of response.content) {
      if (block.type === "tool_use") {
        const input = block.input as PaymentInput;
        const payment = calculatePayment(input.principal, input.annual_rate_pct, input.years);
        results.push({ type: "tool_result", tool_use_id: block.id, content: JSON.stringify({ monthly_payment: payment }) });
      }
    }
    messages.push({ role: "user", content: results });
  }
  throw new Error(`no answer after ${maxSteps} steps`);
}

Core · Instructions and memory

  • A good system prompt has: the role and who the output is for; the steps to follow; the rules (for P1, the lender's guidelines, pasted in full); what to do when data is missing; and the output format.
  • Few-shot examples (one or two worked examples in the prompt) fix tone and format faster than more rules.
  • Chain of thought: older models did better when asked to "think step by step". Reasoning models think on their own; you control how much with reasoning={"effort": "low" | "medium" | "high"}. More effort costs more output tokens and time.
  • Untrusted text: anything a tool returns (CRM notes, emails, web pages) is data. Say so in the instructions, and never let tool text change the rules. P1's data contains one borrower who tries.
  • Memory: short-term memory is the conversation list; long-term memory is anything you save and fetch later (a database, a file). P1 saves each score to SQLite, so tomorrow's run can see yesterday's.
  • Reflection (an evaluator step that checks the answer before it's returned) is the pattern Anthropic calls evaluator-optimizer. P1 uses a light version: a Pydantic validator that rejects a score outside its tier's range.

Core · Testing an agent without the network

You can't unit-test a real model: it's slow, it costs money, and its answers vary. What you can test is your code: that the loop runs the tools it's asked to, sends results back correctly, stops, respects the step limit and survives errors. The trick is the one from Week 0B: give the SDK a fake HTTP transport that returns scripted replies, one per API call.

import itertools
import json

import httpx
from openai import OpenAI

_ids = itertools.count(1)
USAGE = {"input_tokens": 100, "output_tokens": 20, "total_tokens": 120,
         "input_tokens_details": {"cached_tokens": 0}, "output_tokens_details": {"reasoning_tokens": 0}}


def response(output: list) -> dict:
    return {"id": f"resp_{next(_ids)}", "object": "response", "created_at": 0, "model": "gpt-6-luna",
            "status": "completed", "output": output, "usage": USAGE,
            "parallel_tool_calls": True, "tool_choice": "auto", "tools": []}


def function_call(name: str, **arguments) -> dict:
    n = next(_ids)
    return {"type": "function_call", "id": f"fc_{n}", "call_id": f"call_{n}", "name": name,
            "arguments": json.dumps(arguments), "status": "completed"}


def message(text: str) -> dict:
    return {"type": "message", "id": f"msg_{next(_ids)}", "status": "completed", "role": "assistant",
            "content": [{"type": "output_text", "text": text, "annotations": []}]}


def scripted_client(replies: list[dict], requests: list | None = None) -> OpenAI:
    """Each API call gets the next reply; request bodies are saved so tests can inspect them."""
    queue = list(replies)

    def handler(request: httpx.Request) -> httpx.Response:
        if requests is not None:
            requests.append(json.loads(request.content))
        return httpx.Response(200, json=queue.pop(0))

    return OpenAI(api_key="test", http_client=httpx.Client(transport=httpx.MockTransport(handler)))

Save this as tests/fakes.py. It's yours to reuse in every project.

Production reality
  • An answer key must not share code with the system it checks. P1's rules.py imports dti_pct from tools.py. Drop monthly_debts there and the eval still reports 9 of 9, while L-1014 moves from cold (46.2%) to hot (23.7%). Pin hand-computed values from the expected table in tests, independent of both.
  • A fake that accepts anything proves little. If the scripted client returns the next reply whatever it receives, call_id and pairing bugs pass every test and fail on the first real request. Make the fake reject what the API rejects (an output with no matching call, a call with no output) and assert on the recorded request bodies, as this week's drill does.
  • Trim memory only at turn boundaries. Cutting the conversation to the last N items can keep a function_call_output whose call was dropped, and the API rejects the request. Trim at user messages, keep each call with its output, and replace what you drop with a short summary.
  • Test injection on borderline leads. L-1019 fails two hard rules by wide margins (DTI 56.8%, 2% down), so it would stay cold even if the model half-obeyed its note. Put the same note on a lead one condition away from hot, and assert on its tier, its score and that the reasons don't repeat the note. Keep a few such adversarial cases in every eval run.
  • Turn bad production runs into tests. When a run misbehaves, convert its trace.jsonl into scripted replies. The regression test replays the exact sequence of calls offline in milliseconds, and it keeps failing until the code is fixed.

Six bugs in a tool-using agent loop

~60 min

Download ⬇ loop-drill.zip, unzip it, read its README, and run the tests. The code runs, but six tests fail. Each failure is a mistake that shows up in real projects. Fix the code, never the tests, and for each bug write one line in BUGS.md: what was wrong, what a user would have seen in production, and how you fixed it.

Check: all 11 tests pass, offline. Then explain each bug out loud in one sentence, as you would to an interviewer who asks "how would this fail in production?"

Read each failing test's name and assertion before opening the code. The bugs are in agent.py, tools.py.
  1. lead_agent/agent.py (final_assessment): it sends only the dict items of the conversation (the question and the function_call_output items) "to save tokens", dropping the SDK objects: the model's function_call items and reasoning items. Every tool result now points at a call_id that isn't in the input, so the API rejects the request with a 400 and no lead ever gets a score. Fix: send the whole conversation, conversation + [final question]. If you need to save tokens, drop whole call/result pairs, never half of one.
  2. lead_agent/agent.py (run_agent, stop condition): if not calls or response.output_text ends the run whenever the reply contains any text. Models often write a short preamble ("Let me pull the lead record first.") next to a function call, so the loop returns with a call still unanswered: the answer is missing, and the next request fails with a 400. Fix: stop only when the reply contains no function calls.
  3. lead_agent/agent.py (run_agent, step limit): while True replaced for _ in range(max_steps), so max_steps is ignored and the AgentError line is unreachable. A model that keeps asking for tools runs until your budget or a timeout stops it. Fix: loop over range(max_steps) and raise AgentError after the loop.
  4. lead_agent/agent.py (run_agent, parallel calls): call = calls[0] answers only the first function call, a habit carried over from single-call examples. When the model asks for two tools at once (parallel calls are on by default), the next request has a call with no output and the API rejects it with a 400. Fix: loop over every call and append one function_call_output per call before calling the model again.
  5. lead_agent/tools.py (run): except LookupError catches only "not found". Malformed JSON arguments (JSONDecodeError, a ValueError), missing arguments (TypeError) and bad values (ValueError) escape the dispatcher and crash the whole run instead of going back to the model as data. Fix: catch (LookupError, ValueError, TypeError) and return {"error": ...}.
  6. lead_agent/tools.py (list_leads_by_state): the SQL is built with an f-string, so the model's argument becomes part of the query. TX' OR '1'='1 returns every lead in the database; a state with a quote in it crashes with a syntax error. The argument comes from a model that reads untrusted text, so treat it as hostile. Fix: a parameterized query, WHERE property_state = ? with (state.upper(),).

class LeadScore(BaseModel):
    lead_id: str
    score: int
    tier: Literal["hot", "warm", "cold"]
    monthly_payment: float | None
    dti_pct: float | None
    reasons: list[str]
    risks: list[str]
    next_action: str

    @model_validator(mode="after")
    def score_matches_tier(self):
        low, high = TIER_RANGES[self.tier]            # {"hot": (8, 10), "warm": (5, 7), "cold": (1, 4)}
        if not low <= self.score <= high:
            raise ValueError(f"score {self.score} is outside the {self.tier} range {low}-{high}")
        return self
def final_assessment(client, conversation: list, stats: RunStats) -> LeadScore:
    response = client.responses.parse(
        model=MODEL, instructions=INSTRUCTIONS, reasoning={"effort": "low"}, text_format=LeadScore,
        input=conversation + [{"role": "user", "content": "Now give your final assessment of this lead."}])
    stats.add_usage(response.usage)
    if response.output_parsed is None:
        raise AgentError("the model returned no structured assessment (possibly a refusal)")
    return response.output_parsed

Q1

Describe how you would architect an AI agent system, including the agent loop, tool interfaces, memory design, orchestration technologies, and safety considerations.

Salesforce · generative AI system design

Reported Prep-site article: IGotAnOffer ↗. Secondary source; not an official question.

What it probes: Whether you can take the loop you built by hand and explain each part as a design choice with a failure mode, instead of naming frameworks.

  1. Start with the use case and ask whether it needs an agent at all: if the steps are fixed, a workflow with one smart step is cheaper, faster and easier to test (give the cost difference in numbers).
  2. The loop: call the model, append its whole output, run every function call, send each result back by call_id, stop when the model asks for no tools; a step limit, a trace of every call, and token and cost tracking on every run.
  3. Tool interfaces: few tools, strict schemas, descriptions with units and examples, parameterized queries, errors returned as data, and an allow-list checked before dispatch.
  4. Memory: short-term is the conversation (trimmed only at turn boundaries); long-term is storage you query on purpose, such as P1's lead_scores table.
  5. Orchestration: a hand-written loop first so every part is understood; a framework or managed agent service only when it removes real work, and you can still explain what it does underneath.
  6. Safety: tool output is untrusted data, least privilege for tools, side effects behind human approval, validated structured output, and offline tests plus an eval with adversarial cases before launch.

Answers that fail:

  • Naming a framework and stopping there, with no stop condition, step limit or error handling.
  • Treating memory as "add a vector database" without saying what is stored, when it is read, and what it costs.
Q2

How do you handle prompt injection in a customer-facing agent?

Forward deployed engineer roles (several companies) · technical

Aggregated From a public FDE interview guide that lists questions without naming the company for each: Exponent ↗.

What it probes: Whether you know that prompts alone can't stop injection, and can design layers that limit the damage when it gets through.

  1. Name the channels: the user's own messages, and anything tools return (web pages, emails, CRM notes, documents). P1's L-1019 note is a real example.
  2. Treat tool output as data: say so in the instructions and mark it clearly in the input, but don't rely on this alone.
  3. Least privilege: an agent that reads untrusted text gets read-only tools; sending, deleting or paying happens in code, with fixed parameters and a human approval.
  4. Check at the boundaries: an allow-list of tool names before dispatch, parameterized queries, and validated structured output with checks that numbers match tool results.
  5. Test it: adversarial cases in the eval, placed on borderline inputs where a partial effect would show, and monitoring of tool calls in production.

Answers that fail:

  • "Add 'ignore previous instructions' detection to the prompt" as the whole answer.
  • Keyword filters on input, with no mention of what the agent is allowed to do.

Q4

What it probes: Whether you separate testing your code from evaluating the model, and whether your evidence is numbers from real runs.

  3. Numbers per run: agreement with the answer key, tool calls and steps per task, cost per task, error and max-steps rates, repeated across several runs because outputs vary.
  4. Read the traces of every mismatch and decide: model, tool or instructions. Fix the cause and re-run.
  5. In production: log traces, watch error and cost trends, sample outputs for human review, and turn bad runs into regression tests.

Answers that fail:

  • "All my tests pass" when the tests use scripted replies, which prove nothing about model quality.
  • Reporting one run's accuracy with no answer key, no repeat runs and no cost.
Q5

How would you think about designing a creative story-writing agent?

Google · Forward Deployed Engineer · AI/ML round

Reported Candidate write-up (2026), the candidate's paraphrase of the question: Medium ↗. One candidate's report; secondary source.

What it probes: Whether you apply the workflow-vs-agent decision to an open-ended task, and can define quality where there is no answer key.

  1. Clarify: who the user is, story length, interactive or one-shot, content rules, latency and cost targets.
  2. Decide the structure: a fixed pipeline (outline, draft each section, revise) is a workflow and often enough; an agent helps only when the next step truly depends on what was written (for example, checking continuity and choosing what to fix).
  3. Tools and memory: a story bible (characters, places, facts so far) kept as structured data the model reads and updates, because the conversation alone gets long and expensive.
  4. Quality without an answer key: structured checks (continuity against the bible, length, content rules) plus a rubric scored by people or a model grader on a fixed set of prompts.
  5. Limits: a step and cost cap per story, and content-safety checks on both the user's input and the output.

Answers that fail:

  • Designing a multi-agent system before saying why one prompt or a pipeline isn't enough.
  • No way to measure whether the stories got better.
Q6

Here's a junior developer's agent loop. Review it and explain what you'd change or improve.

Anthropic-style design review · agent loop

Format practice Original practice question in the style of Anthropic's design-review question ("Here's a junior developer's design ... review it"), described in IGotAnOffer ↗. Use the broken package from this week's Break it & fix it drill as the code under review.

What it probes: Code-review judgment: finding the bugs that break in production, ordering them by impact, and explaining each fix in one sentence.

  1. Read the loop against the protocol: is the whole response output appended, is every call answered by call_id, is the stop condition "no function calls" rather than text?
  2. Safety nets: a step limit that actually stops, errors returned as data (but logged), and a dispatcher that checks tool names against an allow-list.
  3. Tools: parameterized SQL, not f-strings; strict schemas built by one helper; units in descriptions.
  4. Prioritize out loud: data exposure and crashes first (SQL injection, unhandled exceptions), then protocol errors that make whole runs fail, then cost and clarity.
  5. Say how you'd prevent regressions: a stricter fake that rejects what the API rejects, one test per bug, and a trace for every run.

Answers that fail:

  • Commenting on style and naming while missing the SQL injection and the missing step limit.
  • Listing problems without saying which one to fix first, or how to test that it's fixed.
