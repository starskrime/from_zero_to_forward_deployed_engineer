Summary

  • Workflow: your code decides the steps; the model fills in each one (for example extract, then classify, then draft). Predictable, cheap, easy to test.
  • Agent: the model decides the next step from what it has seen so far, in a loop, until it's done. Flexible, but less predictable and more expensive.
  • Start with the simplest thing that works. Use an agent only when the steps can't be known ahead of time. Many "agents" in production are workflows with one smart step.
  • The agent equation: instructions + tools + memory, run by a model, inside a loop you control (with a step limit, logging and cost tracking).
  • Function calling: you describe tools as JSON schemas. The model never runs anything. It replies with a function_call (a name and JSON arguments); your code runs the function and sends back a function_call_output with the same call_id. Then the model continues.
  • Why tools matter: they give the model fresh data (databases, APIs) and exact computation (math, dates), which is exactly where Week 0C showed models are weakest.
Production reality
  • Every step re-sends everything. The API is stateless, so each request carries the instructions, the tool definitions and every earlier call and result. A run that starts at 2,000 input tokens and grows by 400 per step bills 18,000 input tokens over 6 requests, not the 4,400 you get by counting only new items. Put step counts in your cost estimates, and keep tool results small.
  • Tool definitions cost tokens on every request. Twenty tools with 150-token descriptions add 3,000 input tokens to each request, or 24,000 over an 8-step run, before any work is done. Send only the tools a task needs, and merge tools that are always called together.
  • Units are where tool calls go wrong. Strict mode guarantees that annual_rate_pct is a number, not that it's 6.25 rather than 0.0625. The fraction gives a $1,135.61 payment instead of $2,493.65 on Nadia Aliyeva's loan, and a DTI of 13.9% instead of 26.7%. Put the unit and an example in every numeric description, and have the tool reject implausible values (a mortgage rate below 1% is almost certainly a fraction).
  • Latency grows with steps. Each tool step is a full model round trip, so a 5-request agent takes several times as long as a 1-call workflow on the same model. For batch jobs this is cost and throughput; for a user waiting on a screen, show progress from the trace and stream the final answer.
  • tool_choice applies to each request you send it on. "required" forces a call in every reply, so a loop that always sends it can never finish and every run ends at max_steps. If you must force the first call, send "required" (or a named function) on the first request only, then "auto".

def calculate_payment(principal: float, annual_rate_pct: float, years: int) -> float:
    r = annual_rate_pct / 100 / 12
    n = years * 12

Enterprise · Working on a team's codebase I: small PRs on a customer's repo

Week 0B gave you the basic loop: branch, PR, read your own diff, squash-merge. At a customer you run that loop in a repository you don't own, next to engineers who will maintain your code after you leave. This week's Enterprise track is about fitting into that team. Today: four habits. (TypeScript practice continues in the Bonus module "TypeScript for FDEs".)

  • Small PRs. One change per PR. Google's review guide calls about 100 changed lines "usually reasonable" and 1,000 "usually too large". Small PRs get reviewed sooner and more carefully, and they are easy to revert. "Add the DTI tool" and "rename the rate columns" are two PRs, not one.
  • Branch names the team can read. Use the repository's convention if it has one (look in the README, CONTRIBUTING.md and recent merged PRs). If it has none, type/short-description is common, with the ticket id when there is one: feat/LEND-142-dti-tool, fix/payment-rounding, chore/pr-template.
  • A description a reviewer can act on. Keep 0B's what, why and how tested, and add a fourth part: risk and rollback (what could break, who would notice, how to undo it). Link the ticket. For agent changes, "how tested" includes eval numbers before and after; tomorrow shows why.
  • Draft PRs. gh pr create --draft opens a PR that can't be merged, and code owners aren't asked to review it until you run gh pr ready. Use a draft to show the direction early ("is this the right approach?") and to let CI run before you ask for anyone's time.

When main moved while you worked. Your PR is based on an old main. You have two ways to catch up:

$ git fetch origin
$ git switch feat/LEND-142-dti-tool
$ git rebase origin/main          # replay your commits on top of the new main
# conflict? fix the file, git add it, git rebase --continue (or --abort to start over)
$ pytest -q                       # a rebase with no conflicts can still break the code
$ git push --force-with-lease     # your commits were rewritten, so a plain push is rejected
  • Rebase gives a straight history with your commits on top, but it rewrites them (new commit ids), so the push needs force. Use --force-with-lease, never --force: it refuses to push if someone else pushed to your branch since your last fetch.
  • Merge (git merge origin/main) adds a merge commit and rewrites nothing, so a normal push works. Use it when others also push to your branch.
  • The rule (from Pro Git): don't rebase commits that others may have based work on. Rebase your own branch freely; follow the team's rule for everything else.

Summary

  • Strict mode ("strict": true) makes arguments always match your schema. Its rules: additionalProperties: false on every object, and every property listed in required. An optional field is written as a type that allows null.
  • Descriptions are prompts. Name tools and parameters clearly, give units and examples ("annual rate in percent, e.g. 6.5"), and use enum for fixed choices. The test: could a new colleague use the tool from its description alone?
  • Keep the tool set small (OpenAI suggests fewer than 20 at a time), and merge tools that are always called together.
  • Return errors as data ({"error": "no lead with id L-9999"}) instead of crashing, so the model can recover or explain.
  • Structured output: client.responses.parse(..., text_format=MyModel) makes the model reply in your Pydantic model's shape; read it from response.output_parsed. It's None if the model refused, so check before using it.
  • Tools vs structured output: use tools when the model needs to act or fetch; use structured output when you need its final answer in a shape your code can store.
  • The schema checks shape, not business rules. Add Pydantic validators for rules like "a hot lead must score 8–10".
Production reality
  • Defaults don't make fields optional. responses.parse turns your Pydantic model into a strict schema that lists every field in required, including fields with defaults, so the model always writes a value and your default never applies. For "may be missing", use X | None and decide in code what None means.
  • Truncation isn't a refusal. When the model hits max_output_tokens in the middle of the JSON, responses.parse raises a pydantic ValidationError (type json_invalid); output_parsed is None only for refusals. Reasoning tokens count toward the same limit, so leave headroom, and catch ValidationError for each item in a batch.
  • A valid schema can still hold wrong numbers. Structured output guarantees shape, not truth: a LeadScore can report a 26.7% DTI when the tool returned 46.2%. Before storing, check that monthly_payment and dti_pct equal values in the trace, and reject the assessment if they don't.
  • Errors-as-data can hide your own bugs. A dispatcher that catches TypeError also catches "argument after ** must be a mapping, not str" from a forgotten json.loads, and hands it to the model, which retries until max_steps. Log every error result by tool, alert when a tool's error rate jumps, and unit-test run() directly.
  • Validators fail after you've paid. When a model_validator rejects the output, the tokens are spent and you have nothing to store. Send the validator's message back once and parse again, record how often that happens, and treat a rising rate as a prompt or model problem, not noise.

In Pydantic, str | None with no default becomes "required but nullable" in the schema, which is exactly what strict mode wants. Literal[...] | None gives an enum that also allows null.
from typing import Literal

from openai import OpenAI
from pydantic import BaseModel


class LeadIntake(BaseModel):
    full_name: str | None
    email: str | None
    loan_amount: float | None
    loan_type: Literal["purchase", "refinance"] | None
    property_state: str | None
    credit_score: int | None
    missing_fields: list[str]


INSTRUCTIONS = ("Extract the mortgage lead from the broker's email. Use null for anything not stated; "
                "never guess. property_state is a two-letter US code. List the null fields in missing_fields.")


def extract(client: OpenAI, email_text: str) -> LeadIntake:
    response = client.responses.parse(model="gpt-6-luna", instructions=INSTRUCTIONS,
                                      input=email_text, text_format=LeadIntake)
    if response.output_parsed is None:
        raise ValueError("no structured output (the model may have refused)")
    return response.output_parsed

Enterprise · Working on a team's codebase II: reviewing agent code

At a customer you'll review their engineers' agent code, and they'll review yours. A normal review checks logic, names and tests. Agent code also fails in places a normal review skips, because some of its most important lines aren't code at all. Use this checklist on every PR that touches a prompt, a tool, the loop or the tests.

  1. Prompt and tool-description changes. No compiler checks them, and tests with scripted replies never see them. Read every changed sentence as a rule change. Ask for an eval run before and after (agreement, cost per lead) in the PR. A business rule added to a prompt belongs in rules.py and the guidelines, approved by whoever owns them.
  2. Tool permissions and side effects. For each new tool ask: what can it read, write, send or delete? A tool with side effects in an agent that reads untrusted text needs a guard: an allow-list, an idempotency key, or best, a move out of the agent into code that runs after a person approves.
  3. Bounds. A step limit that still stops the loop, request timeouts, max_output_tokens. Look for while True and for limits that quietly disappeared from a signature.
  4. Secrets and personal data in logs. No key, or any part of one. No borrower names, incomes or notes in application logs, which usually have wider access and longer retention than your trace. Log ids and sizes.
  5. Tests that call the real API. They need a key in CI, cost money, fail at random and fail on forks. Unit tests use scripted replies and assert on what was sent; real-model checks belong in the eval.
  6. Evidence. "Tests pass" says nothing about model behavior. Expect the pytest summary, the eval line and, for a changed path, a trace.

Writing the comments. One comment per problem. Point at the line, label the severity (blocking, suggestion or nit), say what would happen in production, and propose a fix. Start the review with a short summary: approve, or what must change first.

Core · Turning one tool call into an agent

The loop in six lines

repeat up to max_steps:
    response = model(conversation, tools)
    conversation += response.output            # includes reasoning items: send them back
    calls = function calls in response.output
    if no calls: return response.output_text   # the model is done
    for each call: run it, append its function_call_output
  • The stopping condition is "the model asked for no tools", never a keyword in the text.
  • A step limit is your safety net against loops that never end (and bills that never stop).
  • Parallel calls: one response can contain several function calls. Run them all, then call the model once.
  • A dispatcher maps tool names to Python functions, rejects unknown names, and turns exceptions into {"error": ...} results.
  • A trace (each tool, its arguments and its result) is how you debug an agent. Print it now; next week you'll store it.
  • Track tokens and cost across every call in the loop: an agent makes several calls per task.
  • Short-term memory is simply the conversation list. Keep it between questions and the agent can answer follow-ups.
Production reality
  • Single-call loops break on parallel calls. Parallel calls are on by default. A loop that answers only the first call sends a request with an unanswered call, and the API rejects it with a 400; the same rule holds on Claude (a tool_result for every tool_use). If tools depend on each other's results or have side effects, set parallel_tool_calls=False instead of hoping the model calls them one at a time.
  • The SDK retries under your loop. openai-python and anthropic-python retry failed requests twice by default (connection errors, 408, 409, 429 and 5xx), and the default read timeout is 600 seconds. One stuck request can hold an 8-step run for many minutes; set timeout= (and max_retries=) on the client for batch jobs, and log retries so slow runs are explainable.
  • Set max_steps from real traces. Count requests per run on real data, set the limit at roughly twice the typical count, and track how many runs hit it each day. A sudden rise almost always means a tool started returning errors that the model keeps retrying.
  • Big tool results stay in every later request. A list_leads tool that returns 5,000 rows at about 25 tokens each adds 125,000 tokens, re-sent on every following step. Return only the fields the model needs, cap the rows, and say so in the result ("showing 20 of 5,000; filter by state").
  • Side-effect tools need guards. A model can call the same tool twice (in parallel, or after a retry), and text in tool results can steer which tools it calls. Give tools that write or send an idempotency key, check names against an allow-list before dispatch, and move irreversible actions out of the agent into code that a person approves.

from openai import OpenAI


def tool(name, description, properties):
    return {"type": "function", "name": name, "description": description, "strict": True,
            "parameters": {"type": "object", "properties": properties,
                           "required": list(properties), "additionalProperties": False}}


TOOLS = [
    tool("list_leads_by_state", "List leads in a US state: lead_id, full_name, loan_amount, loan_type.",
         {"state": {"type": "string", "description": "Two-letter code, e.g. TX"}}),
    tool("get_lead", "Get one lead's full record.", {"lead_id": {"type": "string"}}),
    tool("calculate_payment", "Monthly principal-and-interest payment for a fixed-rate loan.",
         {"principal": {"type": "number"}, "annual_rate_pct": {"type": "number"}, "years": {"type": "integer"}}),
]


class LeadTools:
    def __init__(self, conn: sqlite3.Connection):
        self.conn = conn

    def list_leads_by_state(self, state: str) -> list[dict]:
        rows = self.conn.execute("SELECT lead_id, full_name, loan_amount, loan_type FROM leads "
                                 "WHERE property_state = ?", (state.upper(),)).fetchall()
        return [dict(zip(["lead_id", "full_name", "loan_amount", "loan_type"], r)) for r in rows]

    def get_lead(self, lead_id: str) -> dict:
        cur = self.conn.cursor()
        cur.row_factory = sqlite3.Row                 # dict-like rows, for this query only
        row = cur.execute("SELECT * FROM leads WHERE lead_id = ?", (lead_id,)).fetchone()
        if row is None:
            raise LookupError(f"no lead {lead_id}")
        return dict(row)

    def calculate_payment(self, principal: float, annual_rate_pct: float, years: int) -> dict:
        r, n = annual_rate_pct / 100 / 12, years * 12
        return {"monthly_payment": round(principal * r / (1 - (1 + r) ** -n), 2)}

    def run(self, name: str, arguments: str) -> str:
        if name not in {t["name"] for t in TOOLS}:
            return json.dumps({"error": f"unknown tool {name}"})
        try:
            return json.dumps(getattr(self, name)(**json.loads(arguments)))
        except (LookupError, ValueError, TypeError) as e:
            return json.dumps({"error": str(e)})


def run_agent(client, tools: LeadTools, conversation: list, max_steps: int = 6) -> str:
    for step in range(1, max_steps + 1):
        response = client.responses.create(
            model="gpt-6-luna", input=conversation, tools=TOOLS,
            instructions="Answer questions about mortgage leads. Use tools for data and math.")
        conversation += response.output
        calls = [i for i in response.output if i.type == "function_call"]
        if not calls:
            return response.output_text
        for call in calls:
            result = tools.run(call.name, call.arguments)
            print(f"step {step}: {call.name}({call.arguments}) -> {result[:100]}")
            conversation.append({"type": "function_call_output", "call_id": call.call_id, "output": result})
    raise RuntimeError(f"no answer after {max_steps} steps")

Enterprise · Working on a team's codebase III: CI that runs your tests

Continuous integration (CI) runs the test suite on a clean machine for every pull request, so "it works on my laptop" stops being the bar. GitHub Actions reads workflow files from .github/workflows/. A workflow has triggers (on:), one or more jobs that each run on a fresh virtual machine, and steps inside each job. P1 needs one job: get the code, set up Python, install the requirements, run pytest.

  • Triggers. pull_request runs when a PR is opened or reopened and on every new push to it. Add push on main so the state of main is checked too.
  • Action versions. Pin each action to a major version: actions/checkout@v7 and actions/setup-python@v7 were the current majors in October 2026. Check each action's Releases page when you set up a repo; examples in GitHub's own docs can be a major or two behind.
  • Cache pip. cache: pip on setup-python saves pip's download cache, keyed on a hash of requirements.txt, so later runs skip most downloads. Pinned versions (your 0A pip freeze habit) keep the key stable.
  • No API key for unit tests. Your tests use scripted replies, so CI needs no key. Don't add one "just in case": a test that needs it is calling the real model. With the key unset, OpenAI() raises an error, and that's the alarm you want. GitHub also doesn't pass secrets to workflows triggered from forks (except GITHUB_TOKEN), so such a test would fail for outside contributors anyway. Runs that need a key, like the eval, are started by hand or on a schedule, not on every PR.
  • Least privilege. permissions: contents: read limits what the workflow's token can do. timeout-minutes stops a hung job before it burns minutes.
  • Fail loudly. pytest exits with code 5 when it collects no tests, which fails the job, so a run that finds no tests (a misnamed file, a wrong folder) can't pass quietly. The job's name, test, is the check you'll make required tomorrow.

Core · Testing an agent without the network

You can't unit-test a real model: it's slow, it costs money, and its answers vary. What you can test is your code: that the loop runs the tools it's asked to, sends results back correctly, stops, respects the step limit and survives errors. The trick is the one from Week 0B: give the SDK a fake HTTP transport that returns scripted replies, one per API call.

import itertools
import json

import httpx
from openai import OpenAI

_ids = itertools.count(1)
USAGE = {"input_tokens": 100, "output_tokens": 20, "total_tokens": 120,
         "input_tokens_details": {"cached_tokens": 0}, "output_tokens_details": {"reasoning_tokens": 0}}


def response(output: list) -> dict:
    return {"id": f"resp_{next(_ids)}", "object": "response", "created_at": 0, "model": "gpt-6-luna",
            "status": "completed", "output": output, "usage": USAGE,
            "parallel_tool_calls": True, "tool_choice": "auto", "tools": []}


def function_call(name: str, **arguments) -> dict:
    n = next(_ids)
    return {"type": "function_call", "id": f"fc_{n}", "call_id": f"call_{n}", "name": name,
            "arguments": json.dumps(arguments), "status": "completed"}


def message(text: str) -> dict:
    return {"type": "message", "id": f"msg_{next(_ids)}", "status": "completed", "role": "assistant",
            "content": [{"type": "output_text", "text": text, "annotations": []}]}


def scripted_client(replies: list[dict], requests: list | None = None) -> OpenAI:
    """Each API call gets the next reply; request bodies are saved so tests can inspect them."""
    queue = list(replies)

    def handler(request: httpx.Request) -> httpx.Response:
        if requests is not None:
            requests.append(json.loads(request.content))
        return httpx.Response(200, json=queue.pop(0))

    return OpenAI(api_key="test", http_client=httpx.Client(transport=httpx.MockTransport(handler)))

Save this as tests/fakes.py. It's yours to reuse in every project.

Production reality
  • An answer key must not share code with the system it checks. P1's rules.py imports dti_pct from tools.py. Drop monthly_debts there and the eval still reports 9 of 9, while L-1014 moves from cold (46.2%) to hot (23.7%). Pin hand-computed values from the expected table in tests, independent of both.
  • A fake that accepts anything proves little. If the scripted client returns the next reply whatever it receives, call_id and pairing bugs pass every test and fail on the first real request. Make the fake reject what the API rejects (an output with no matching call, a call with no output) and assert on the recorded request bodies, as this week's drill does.
  • Trim memory only at turn boundaries. Cutting the conversation to the last N items can keep a function_call_output whose call was dropped, and the API rejects the request. Trim at user messages, keep each call with its output, and replace what you drop with a short summary.
  • Test injection on borderline leads. L-1019 fails two hard rules by wide margins (DTI 56.8%, 2% down), so it would stay cold even if the model half-obeyed its note. Put the same note on a lead one condition away from hot, and assert on its tier, its score and that the reasons don't repeat the note. Keep a few such adversarial cases in every eval run.
  • Turn bad production runs into tests. When a run misbehaves, convert its trace.jsonl into scripted replies. The regression test replays the exact sequence of calls offline in milliseconds, and it keeps failing until the code is fixed.

Enterprise · Working on a team's codebase IV: guardrails in the repo

Reviews and CI catch problems after you push. Today's guardrails catch them earlier, or make the team's rules impossible to skip. Customers' repositories usually have most of them; you should know what each one does before your first PR there.

  • ruff: lint and format in one tool. ruff check finds bugs and style problems, ruff check --fix fixes the mechanical ones, and ruff format formats the code. Configure it in pyproject.toml and list the rules explicitly: ruff's default rule set changes between versions (0.16 turns on several hundred rules), and an explicit list means an upgrade can't change what CI checks.
  • pre-commit. It runs checks on your staged files at every git commit. Install it with pip, describe the hooks in .pre-commit-config.yaml, run pre-commit install once per clone, and pre-commit run --all-files for the first pass. Hooks only run where someone installed them, and git commit --no-verify skips them, so CI runs the same checks.
  • Branch protection on main (Settings → Branches). Require a pull request; require status checks (test, lint); optionally require branches to be up to date before merging (that's when you'll rebase, as on Day 1); require review from code owners. Admins can bypass these rules unless "Do not allow bypassing the above settings" is on. Free for public repositories; private ones need a paid plan. Many organizations now use rulesets, which do the same job.
  • CODEOWNERS. .github/CODEOWNERS maps paths to people or teams. Owners are asked to review automatically (not on drafts), and with branch protection one owner's approval is required. The last matching pattern wins, so put broad patterns first. Owners need write access. At a lender, compliance would own rules.py and guidelines.md, so no rule change merges without them.
  • Secrets discipline. The 0A rule stands: a key that was ever pushed is rotated first; cleaning history comes after. Now check for it: git ls-files | grep -i env should list only .env.example, and git log --all --oneline -S "sk-" lists every commit that added or removed a key-like string. The detect-private-key hook catches private key files, not API keys. GitHub's push protection blocks many known key formats and is on by default for public repositories: a safety net, not the plan. At a customer, a leaked key is also an incident: tell their security contact the same day, through their process.

Problem 1

Sliding-window rate limiter for model calls

~30 min

Your agent calls a model API that allows at most n requests in any window of w seconds. Go over the limit and you get 429 errors and retries that cost money. Build a limiter that your loop asks before every call.

allow(t) is called with the current time t in seconds. It returns True and records the call if fewer than n allowed calls happened in the window (t - w, t]. Otherwise it returns False and records nothing: a rejected call uses no budget. A call made exactly w seconds ago has left the window.

Signature

class RateLimiter:
    def __init__(self, n: int, w: float): ...
    def allow(self, t: float) -> bool: ...

Examples

rl = RateLimiter(n=2, w=10)
rl.allow(1)    # True
rl.allow(2)    # True
rl.allow(3)    # False  (2 calls in (-7, 3])
rl.allow(11)   # True   (the call at 1 left the window)
rl.allow(12)   # True   (the call at 2 left the window)
rl.allow(13)   # False

Constraints

  • t never decreases between calls; several calls may share the same t.
  • 0 ≤ n ≤ 10^5, w > 0, up to 10^6 calls to allow.
  • allow must be amortized O(1). Memory must not grow with the number of calls.

What interviewers look for: A deque of allowed timestamps, expiring from the left. A clear answer to "is the window edge open or closed?" and the amortized O(1) argument: each timestamp is pushed once and popped once.

Check: (1) The example above gives [True, True, False, True, True, False]. (2) RateLimiter(1, 5): allow(0) → True, allow(4) → False, allow(5) → True (the rejected call at 4 must not count). (3) RateLimiter(3, 1): five calls at t=7 give [True, True, True, False, False].

Keep only the times of allowed calls, oldest first, in a collections.deque. On each call, pop from the left while the oldest time is <= t - w. Then the deque length is the number of calls in the window. Since times only grow, expired items are always at the left. The deque never holds more than n items.

from collections import deque


class RateLimiter:
    """Sliding-window rate limiter: at most n allowed calls in any window of w seconds.

    A call at time t counts against every later call at time t2 with t2 - t < w.
    Only allowed calls are recorded; rejected calls use no budget.

    Complexity: allow() is amortized O(1) time (each timestamp is appended
    once and popped at most once). Space O(n): the deque never holds more
    than n timestamps.
    """

    def __init__(self, n: int, w: float):
        if n < 0 or w <= 0:
            raise ValueError("n must be >= 0 and w must be > 0")
        self.n = n
        self.w = w
        self.calls = deque()  # times of allowed calls, oldest first

    def allow(self, t: float) -> bool:
        # Drop calls that are out of the window (t - w, t].
        while self.calls and self.calls[0] <= t - self.w:
            self.calls.popleft()
        if len(self.calls) < self.n:
            self.calls.append(t)
            return True
        return False

Complexity: allow is amortized O(1): each timestamp is appended once and popped at most once. Space O(n).

Problem 2

Is the streamed JSON balanced?

~30 min

You stream structured output from a model and want to know, before parsing, whether the text has balanced brackets. A cheap check like this lets you detect a truncated reply (for example one cut off by max_output_tokens) and retry.

Return True if every { and [ is closed by the matching } and ] in the right order. Brackets inside double-quoted strings do not count. Inside a string, a backslash escapes the next character, so \" does not end the string. A string that never closes makes the text unbalanced. Only {} and [] matter; other characters are ignored.

Signature

def is_balanced(text: str) -> bool: ...

Examples

is_balanced('{"a": [1, 2, {"b": []}]}')   # True
is_balanced('{"a": "}]{["}')              # True: brackets are inside a string
is_balanced('{"a": "\\"}"}')              # True: the string is \"} (escaped quote)
is_balanced('[{]}')                       # False: crossed
is_balanced('{"a": [1, 2]')               # False: truncated
is_balanced('{"a": "unterminated}')       # False: string never closes

Constraints

  • 0 ≤ len(text) ≤ 10^6. Nesting can be 10^4 deep, so avoid recursion.
  • One pass, O(n) time.
  • You don't need to validate JSON itself (commas, keys, numbers). Only brackets and strings.

What interviewers look for: A stack for brackets plus two flags (in_string, escaped), checked in the right order. Candidates who handle the escape case without being asked, and who name the unterminated-string case, stand out.

Check: (1) is_balanced('{"a": "\\"}"}') (the string holds an escaped quote and a brace) → True. (2) is_balanced('["\\\\"]') → True: an escaped backslash, then the quote really closes the string. (3) is_balanced("{}}") → False and is_balanced("") → True.

Walk the text once with a tiny state machine. Outside a string: a quote enters the string, an opener is pushed, a closer must match the top of the stack. Inside a string: if the previous character was a backslash, skip this one; a backslash sets escaped; a quote leaves the string; everything else is ignored. At the end the text is balanced only if the stack is empty and you are not inside a string.

def is_balanced(text: str) -> bool:
    """Return True if {} and [] in text are balanced, ignoring brackets inside
    double-quoted strings. Inside a string, a backslash escapes the next
    character (so \\" does not end the string). An unterminated string is
    not balanced.

    Complexity: O(n) time, one pass. O(d) extra space, where d is the
    deepest nesting.
    """
    pairs = {"}": "{", "]": "["}
    stack = []
    in_string = False
    escaped = False
    for ch in text:
        if in_string:
            if escaped:
                escaped = False
            elif ch == "\\":
                escaped = True
            elif ch == '"':
                in_string = False
        elif ch == '"':
            in_string = True
        elif ch in "{[":
            stack.append(ch)
        elif ch in "}]":
            if not stack or stack.pop() != pairs[ch]:
                return False
    return not stack and not in_string

Complexity: O(n) time, one pass. O(d) extra space for the stack, where d is the deepest nesting.
