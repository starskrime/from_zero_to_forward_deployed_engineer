Summary: the ten facts to know

  1. An LLM predicts the next token. Given a sequence of tokens, it outputs a probability for every token in its vocabulary. Generation is a loop: pick one token, append it, predict again.
  2. Tokens are chunks of text, often word pieces. In English a token averages about 4 characters (about ¾ of a word). You pay, wait and hit limits in tokens, not words.
  3. Tokenizers differ by provider. The same text gives different counts on OpenAI, Claude and Gemini, and even between model generations of one provider.
  4. Other languages, code and numbers often need more tokens per character. The same message can cost more in Azerbaijani or Japanese than in English.
  5. Models see tokens, not letters. That's why counting letters or reversing words can trip them up.
  6. Pretraining on internet-scale text produces a base model that continues documents. Post-training (examples of conversations, then reinforcement learning) turns it into an assistant.
  7. The context window is the maximum number of tokens the model can take in (and usually produce) in one call. Everything it "knows" about your task must fit there.
  8. The model has no memory between calls. Chat apps resend the whole conversation every turn, so long chats cost more each turn.
  9. Knowledge has a cutoff date. Anything newer must come from your prompt, a search or a tool.
  10. Output is sampled, so the same prompt can give different answers. Day 2 explains why.
Production reality
  • Estimate tokens from the customer's real text. "About 4 characters per token" is English prose. Support tickets in other languages, pasted logs, JSON and long numbers all run higher. Before quoting a cost, count 50–100 real messages with each provider's own counter (Claude's and Gemini's count_tokens); tiktoken only counts for OpenAI.
  • Every call re-sends the whole conversation. With a 500-token system prompt, 100-token questions and 200-token replies, a 10-turn chat bills 19,500 input tokens, not 3,500. Cap the history, summarize old turns, and put stable text first so it can be cached.
  • Guard limits in tokens, and leave room for the answer. A len(text) / 4 check lets a 300,000-character Japanese contract through as "75,000 tokens". Count real tokens before sending, and keep headroom for the output (including hidden reasoning) inside the context window.
  • Re-measure when you change model generation. Tokenizers change between generations of the same provider (newer Claude models produce more tokens for the same text), so an upgrade at the same price per token can still raise the bill. Re-run your token counts and cost table on every model change.
  • The knowledge cutoff shows up as confident, outdated answers. Rates, prices, product names and policies that changed after the cutoff come back without any warning. Put current facts in the prompt or behind a tool, and add questions about recent changes to your test set.

Summary

  • The pipeline: tokens → embedding vectors → many layers of attention (tokens look at earlier tokens to gather context) and MLPs (where much of the stored knowledge lives) → a score (logit) for every possible next token → softmax turns scores into probabilities.
  • Why long prompts cost more and run slower: every token attends to the tokens before it, so the work grows with context length. Keep context lean; you'll see this again in context engineering (Weeks 4 and 8).
  • Temperature divides the logits before softmax. Below 1 sharpens the distribution (more predictable), above 1 flattens it (more varied). Temperature 0 means "always take the top token" (greedy).
  • Top-p (nucleus sampling) keeps only the smallest set of top tokens whose probabilities add up to p, then samples among them.
  • Newer models are removing these settings. Recent Claude models only accept the default temperature, GPT-6 accepts temperature only with reasoning turned off, and Google recommends leaving Gemini 3 at its defaults. For consistent outputs, rely on clear instructions, structured output and evals, not temperature.
  • Even temperature 0 isn't perfectly repeatable across calls. Design systems that tolerate small variations.
  • Hallucination is a fluent guess. Training and benchmarks have rewarded guessing over saying "I don't know". Reduce it by giving the model the facts (retrieval, tools), explicitly allowing "I don't know", and asking for quotes from sources.
Production reality
  • Sampling settings are disappearing from the APIs. The Claude Python SDK's messages.create() has no temperature parameter (passing one raises TypeError before any request is sent), gpt-6-luna accepts temperature only with reasoning effort "none", and Google recommends Gemini 3's defaults. Keep sampling settings per model in config, never hard-coded in shared code.
  • You can't promise deterministic output. Even at temperature 0, repeated calls can differ. Write checks that accept equivalent answers (normalize case and whitespace, compare parsed fields), and run each test prompt several times before trusting a pass rate.
  • Settings compound. On the lesson's logits, temperature 0.5 plus top_p 0.95 leaves only " Paris" in the nucleus, so the model is effectively greedy. Change one knob at a time and measure after each change.
  • Test samplers against known values, not just invariants. A softmax that divides by the temperature after exp still sums to 1, yet temperature then has no effect at all. Assert exact probabilities at two or more temperatures, and check which tokens top-p keeps.
  • Measure how often the model abstains. Once you allow "I don't know", track how often it says so on questions that do have answers and on ones that don't. Both rates matter: a bot that never abstains is guessing, one that always abstains is useless.

Softmax: divide each logit by the temperature, take math.exp of each, then divide each by their total. Subtract the largest scaled logit before exp: it doesn't change the result but prevents overflow with big numbers. For top-p, sort by probability, highest first, and add tokens until the running total reaches p.
softmax: scaled = logit / T → m = max(scaled) → e = exp(s − m) → p = e / sum(e) · top_p: for tok, prob in sorted(desc): keep; total += prob; if total ≥ p: stop → renormalize · sample: if T == 0 → greedy; else rng.choices(tokens, weights=probs)

import math
import random
from collections import Counter


def softmax(logits: dict[str, float], temperature: float = 1.0) -> dict[str, float]:
    """Turn raw scores into probabilities. Lower temperature = sharper."""
    if temperature <= 0:
        raise ValueError("temperature must be > 0 (use greedy() for temperature 0)")
    scaled = {tok: score / temperature for tok, score in logits.items()}
    biggest = max(scaled.values())                      # subtract the max for numerical safety
    exps = {tok: math.exp(s - biggest) for tok, s in scaled.items()}
    total = sum(exps.values())
    return {tok: e / total for tok, e in exps.items()}


def greedy(logits: dict[str, float]) -> str:
    return max(logits, key=logits.get)


def top_p_filter(probs: dict[str, float], p: float) -> dict[str, float]:
    """Keep the most likely tokens until their total reaches p, then renormalize."""
    kept, running = {}, 0.0
    for tok, prob in sorted(probs.items(), key=lambda kv: kv[1], reverse=True):
        kept[tok] = prob
        running += prob
        if running >= p:
            break
    total = sum(kept.values())
    return {tok: prob / total for tok, prob in kept.items()}


def sample(logits: dict[str, float], temperature: float = 1.0, top_p: float = 1.0,
           rng: random.Random | None = None) -> str:
    if temperature == 0:
        return greedy(logits)
    rng = rng or random.Random()
    probs = top_p_filter(softmax(logits, temperature), top_p)
    return rng.choices(list(probs), weights=list(probs.values()), k=1)[0]

Production reality
  • Read text by block type, never by position. Claude's content is a list: content[0].text raises AttributeError: 'ThinkingBlock' object has no attribute 'text' when thinking is on, and silently drops text when there are several text blocks. Join every block whose type is "text".
  • Empty answers are normal; handle them. When hidden reasoning uses the whole output limit, OpenAI returns output_text == "" with status="incomplete" (incomplete_details.reason="max_output_tokens"), and Gemini returns r.text is None with finish reason MAX_TOKENS. Store the stop/finish reason with every result, leave headroom in the limit, and alert on empty answers.
  • Usage fields don't mean the same thing everywhere. Claude's input_tokens counts only tokens after the last cache breakpoint; total input is cache_read_input_tokens + cache_creation_input_tokens + input_tokens (Claude docs ↗). Gemini's candidates_token_count excludes thoughts_token_count. Convert everything to one convention in your adapter, and test it with mocked responses.
  • Measure TTFT at the first text, not the first event. Streams open with lifecycle events (response.created on OpenAI, message_start on Claude) before any text. Record both TTFT and total time: total ≈ TTFT + output tokens ÷ tokens per second, so at 0.6 s and 80 tokens/s a 400-token answer takes 5.6 s.
  • A sync client inside async code runs everything in series. Calling anthropic.Anthropic() inside async def blocks the event loop: 300 two-second calls take about 600 s even with Semaphore(10), instead of about 60 s. Use AsyncOpenAI, AsyncAnthropic and Gemini's client.aio.

import os

import httpx


def raw_claude(client: httpx.Client, prompt: str, model: str = "claude-haiku-4-5") -> dict:
    resp = client.post(
        "https://api.anthropic.com/v1/messages",
        headers={"x-api-key": os.environ["ANTHROPIC_API_KEY"],
                 "anthropic-version": "2023-06-01",
                 "content-type": "application/json"},
        json={"model": model, "max_tokens": 200,
              "messages": [{"role": "user", "content": prompt}]},
        timeout=30.0,
    )
    resp.raise_for_status()
    body = resp.json()
    return {"text": body["content"][0]["text"], "usage": body["usage"], "stop_reason": body["stop_reason"]}

import time

import anthropic
import openai
from google import genai
from google.genai import types
from pydantic import BaseModel


class Answer(BaseModel):
    provider: str
    model: str
    text: str
    input_tokens: int
    output_tokens: int
    latency_s: float


def ask_openai(client: openai.OpenAI, model: str, system: str, prompt: str, max_tokens: int = 300) -> Answer:
    start = time.perf_counter()
    r = client.responses.create(model=model, instructions=system, input=prompt,
                                max_output_tokens=max_tokens, reasoning={"effort": "none"})
    return Answer(provider="openai", model=model, text=r.output_text,
                  input_tokens=r.usage.input_tokens, output_tokens=r.usage.output_tokens,
                  latency_s=time.perf_counter() - start)

Core · Embeddings: meaning as numbers

  • An embedding is a list of numbers (for example 1,536 of them) that represents the meaning of a text. Texts with similar meaning get vectors that point in similar directions, even with no words in common.
  • Cosine similarity measures that direction: 1 = same direction, 0 = unrelated, −1 = opposite. It's the engine of semantic search and of RAG (Week 2).
  • Embedding models are separate, much cheaper models: OpenAI text-embedding-3-small costs $0.02 per 1M tokens; Gemini offers gemini-embedding-001. Anthropic doesn't make one and recommends Voyage AI.
  • Vectors from different embedding models can't be compared with each other. Pick one model per index.

Production reality
  • Prompt caching has a minimum size and a short lifetime. On Claude, cache reads cost 0.1× the input price, writes with the default 5-minute lifetime cost 1.25×, and the minimum cacheable prefix is 4,096 tokens on Haiku 4.5 (1,024 on Sonnet 5) (Claude docs ↗). A 1,200-token system prompt on Haiku 4.5 is below that minimum and won't be cached. Check cache_read_input_tokens in real responses before you promise savings.
  • Budget from measured usage, not from the visible answer. A gpt-6-luna call with 200 visible output tokens and 600 reasoning tokens costs $9.68 per 20,000 calls, not $3.68. Log input, cached, output and reasoning tokens per call, and recompute the monthly estimate from real traffic after the first week.
  • A dot product equals cosine only on unit-length vectors. Scoring with a plain dot product works while every vector has length 1, then ranks long vectors first when you add another model, averaged vectors or your own features. Normalize, or compute cosine; and check vector lengths, because a zip-based cosine accepts vectors of different dimensions without an error.
  • Number checks break on chatty answers. "For a 30-year loan at 6.5%, the payment is $1,798.65" gives 30 to a first-number regex. Ask for the value alone or in a named JSON field, log the raw reply of every failed check, and read a sample of failures before you trust a pass rate.
  • Injection defenses belong in the architecture. Keyword filters ("ignore previous instructions") are bypassed by rewording. Put injection tests in every channel the system reads (emails, PDFs, web pages, tool results), and remove at least one leg of the trifecta: no private data, no untrusted input, or no way to send data out without human approval.

Check: cosine([1,2,3], [2,4,6]) = 1.0, cosine([1,2,3], [-1,-2,-3]) = −1.0, cosine([1,2,3], [3,-1,0]) ≈ 0.0845. Each query's top result is the matching FAQ (password reset, charged twice, SSO) even though they share almost no words. That's semantic search.

Embed the documents and the query together in one call (one request, one bill), then split the result: the last vector is the query. Score every document against the query and sort, highest first.
import math

import openai


def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b)


def embed(client: openai.OpenAI, texts: list[str], model: str = "text-embedding-3-small") -> list[list[float]]:
    resp = client.embeddings.create(model=model, input=texts)
    return [item.embedding for item in resp.data]


def search(client: openai.OpenAI, query: str, docs: list[str], k: int = 3) -> list[tuple[float, str]]:
    vectors = embed(client, docs + [query])
    doc_vecs, q = vectors[:-1], vectors[-1]
    scored = sorted(((cosine(q, v), d) for v, d in zip(doc_vecs, docs)), reverse=True)
    return scored[:k]

Core · Cost and latency math

  • Cost per call = input tokens × input price + output tokens × output price (prices are per 1M tokens). Output usually costs 5× or more than input, and hidden reasoning tokens count as output.
  • Monthly cost = cost per call × calls per month. FDEs estimate this before building, then measure it after.
  • Prompt caching: a long, repeated prefix (system prompt, documents) can be billed at about a tenth of the input price on later calls.
  • Batch APIs cost 50% less on all three providers, when an answer can wait up to a day.
  • Latency ≈ time to first token + output tokens ÷ output speed (tokens per second). Long answers are slow answers; ask for short outputs where you can.

NUMBER = re.compile(r"-?\d[\d,]*(?:\.\d+)?")


def extract_number(text: str) -> float | None:
    match = NUMBER.search(text)
    return float(match.group().replace(",", "")) if match else None


def strip_fences(text: str) -> str:
    return re.sub(r"^```(?:json)?\s*|\s*```$", "", text.strip())


def parse_json_reply(text: str) -> dict | None:
    try:
        data = json.loads(strip_fences(text))
    except json.JSONDecodeError:
        return None
    return data if isinstance(data, dict) else None

Core · A first look at prompt injection

Six bugs in LLM plumbing: sampling, pricing, latency, similarity and provider adapters

~60 min

Download ⬇ llm-drill.zip, unzip it, read its README, and run the tests. The code runs, but six tests fail. Each failure is a mistake that shows up in real projects. Fix the code, never the tests, and for each bug write one line in BUGS.md: what was wrong, what a user would have seen in production, and how you fixed it.

Check: all 33 tests pass, offline. Then explain each bug out loud in one sentence, as you would to an interviewer who asks "how would this fail in production?"

Read each failing test's name and assertion before opening the code. The bugs are in sampler.py, pricing.py, similarity.py, providers.py, checks.py.
  1. sampler.py (softmax): the temperature divides the probabilities after exp instead of dividing the logits before it. Normalizing then cancels the division, so temperature has no effect at all: T = 0.5 gives Paris 0.785 instead of 0.973, and a customer who lowers the temperature for more predictable answers sees no change. Fix: scaled = logit / T first, subtract the largest scaled logit, then exp and normalize.
  2. sampler.py (top_p_filter): the loop checks whether the next token would push the total past p before adding it, so it stops one token too early. At p = 0.9 it keeps Paris and Lyon (0.891 in total, short of 0.9) and drops " the", so sampling is narrower than the setting promises. Fix: add the token first, then stop once the running total reaches p.
  3. pricing.py (cost_usd): cached tokens are billed twice: once at the full input price (fresh = input_tokens) and again at the cached price. Turning on prompt caching makes the estimate go up ($114.80 instead of $66.80 a month for the Sonnet 5 triage example), which can kill a good design in a cost review. Fix: fresh = input_tokens - cached_tokens.
  4. similarity.py (cosine): it returns the dot product without dividing by the two lengths. cosine([1,2,3],[2,4,6]) returns 28 instead of 1.0, and with vectors that aren't normalized, long vectors win the ranking whatever they mean. It happens to work on unit-length vectors, which is why it slips through. Fix: divide by norm(a) * norm(b).
  5. providers.py (ask_claude): the text is read from msg.content[0]. When the reply starts with a thinking block (or has several text blocks), this raises AttributeError: 'ThinkingBlock' object has no attribute 'text' or silently drops the rest of the answer. Fix: join the text of every block whose type == "text".
  6. checks.py (extract_number): the pattern -?\d+(?:\.\d+)? has no room for thousands separators, so "$1,798.65" is read as 1.0 and a correct mortgage answer fails the bench's number check. Fix: -?\d[\d,]*(?:\.\d+)? and remove the commas before float().

async def run_one(provider, prompt: Prompt, sem: asyncio.Semaphore, max_tokens: int) -> Result:
    async with sem:
        start = time.perf_counter()
        try:
            c = await provider.complete(SYSTEM, prompt.text, max_tokens)
        except Exception as e:                      # one failure must never stop the whole bench
            return Result(prompt_id=prompt.id, provider=provider.name, model=provider.model,
                          latency_s=time.perf_counter() - start, error=str(e))
        return Result(prompt_id=prompt.id, provider=provider.name, model=provider.model, text=c.text,
                      input_tokens=c.input_tokens, output_tokens=c.output_tokens,
                      latency_s=time.perf_counter() - start,
                      cost_usd=cost_usd(provider.name, c.input_tokens, c.output_tokens),

async def run_bench(providers, prompts, concurrency=4, repeat=1, max_tokens=400) -> list[Result]:
    sem = asyncio.Semaphore(concurrency)
    tasks = [run_one(p, q, sem, max_tokens) for p in providers for q in prompts for _ in range(repeat)]
    return await asyncio.gather(*tasks)

Q1

What is KV cache? How does it help in LLM inference?

Apple · role not specified · LLM fundamentals

Reported Interview-prep article citing candidate reports: IGotAnOffer ↗. Secondary source; not an official question.

What it probes: Whether you understand generation as a loop and can connect it to latency, memory and cost. This week supports the level below; later weeks on serving cost and context go deeper.

  1. Start from generation: the model produces one token at a time, and each new token attends to all the tokens before it.
  2. Inside every attention layer, each token gets a key and a value vector. For tokens already processed these don't change, so recomputing them for the whole prefix at every step is wasted work.
  3. The KV cache stores those keys and values per layer, so each new step only computes the newest token and attends to the cached ones. Without it, every step would recompute keys and values for the entire sequence so far.
  4. Connect it to latency: reading the prompt (filling the cache) is what you wait for before the first token (TTFT); after that, tokens come at a steady speed. That's the TTFT + tokens ÷ speed model from Day 4.
  5. The cost: the cache takes memory that grows with context length (and with the number of layers and parallel requests), one reason long contexts are expensive to serve.
  6. Link to what you use as an FDE: provider prompt caching applies the same idea across requests, reusing the processed prefix of a repeated system prompt, which is why cached input is billed at about a tenth of the price and starts faster.

Answers that fail:

  • "It caches answers to repeated questions" (that's a response cache, a different thing).
  • Reciting the definition without connecting it to TTFT, memory or cost.
  • Claiming it makes long prompts free: the prompt still has to be processed once, and the cache uses memory.
Q2

A customer demands sub-100 ms latency for LLM search; naive RAG takes 1.5 s. Get to 100 ms.

Several companies (not named) · Forward Deployed Engineer · latency

Aggregated Public question list in a prep guide, no company named: Exponent FDE guide ↗. Secondary source.

What it probes: Whether you decompose latency into measured parts, know which LLM levers exist, and renegotiate what must be fast instead of promising the impossible. Answer with this week's levers; retrieval tuning comes in Weeks 2–3.

  1. Clarify what must happen in 100 ms: showing results, the first words, or a complete generated answer? Those are very different targets.
  2. Measure before you change anything: time each stage (embed the query, retrieve, time to first token, generation) with perf_counter over many runs, and look at the slow runs (p95), not just the average.
  3. Use the latency model: total ≈ TTFT + output tokens ÷ speed. If the model's TTFT alone is above 100 ms, no prompt tweak gets a generated answer there. Even at 250 tokens/s, 20 output tokens take 80 ms.
  4. LLM levers: a smaller, faster model with reasoning off; much shorter outputs (a label or a one-line answer, not a paragraph); a shorter prompt with the stable prefix first so it's cached; stream so the first words appear early.
  5. Take the LLM off the hot path: return the ranked results within 100 ms and stream a generated summary afterwards; pre-compute answers for frequent queries offline (batch API at half price) and serve them from a cache.
  6. Close with the trade-off, in numbers: what each option costs and what quality it gives up, measured on the customer's own queries.

Answers that fail:

  • Promising 100 ms for a full generated answer without measuring anything.
  • Only tuning the prompt or the vector database while the model's generation time dominates.
  • Never asking which part of the experience actually needs to be that fast.
Q3

When do you fine-tune vs. RAG vs. prompt-engineer?

Several companies (not named) · Forward Deployed Engineer · judgment

Aggregated Public question list in a prep guide, no company named: Exponent FDE guide ↗. A close variant ("Should we fine-tune or use RAG here?") appears in an interviewer's write-up ↗. Secondary sources.

What it probes: Whether you diagnose the problem type (missing knowledge vs. wrong behavior) and decide with measurements, starting with the cheapest option.

  1. First ask what's failing, and measure it: a small labeled set and a bench like this week's, so every option is judged on the same prompts.
  2. Prompt engineering first: clear instructions, exact format, examples, permission to say "I don't know". It's the cheapest option and the quickest to change.
  3. Missing or changing knowledge (private documents, facts after the cutoff, answers that must cite sources) means putting the facts in the context: retrieval (RAG, Week 2). Training facts into weights makes them hard to update or cite.
  4. Behavior problems that good prompts can't fix, at high volume (a consistent format or style, a narrow classification task), are where fine-tuning can pay off, sometimes letting a smaller, cheaper, faster model do the job.
  5. Weigh cost and operations: fine-tuning needs labeled data, re-training when models change, and its own evals; RAG needs an ingestion pipeline and permissions.
  6. Often the answer is a combination; say what evidence would make you switch.

Answers that fail:

  • "Always fine-tune for domain knowledge."
  • Choosing a technique before identifying whether the problem is knowledge or behavior.
  • No mention of how you'd measure that the choice worked.
Q4

Explain why your RAG system can't guarantee 100% accuracy to a non-technical VP.

Several companies (not named) · Forward Deployed Engineer · communication

Aggregated Public question list in a prep guide, no company named: Exponent FDE guide ↗. Secondary source. Practice it for LLM systems in general this week; add retrieval misses after Week 2.

What it probes: Whether you can explain probabilistic behavior without jargon or defensiveness, and turn "not 100%" into a managed business risk.

  1. Lead with the business answer: "No system that reads free text is perfect, including people. What matters is that we know the error rate, keep it below today's, and catch the costly mistakes."
  2. One plain sentence on why: the model writes the most likely next words, based on patterns; when the facts it needs aren't in front of it, it can produce a fluent guess.
  3. Compare with today's baseline in their numbers: for example, 12% of claims emails reach the wrong team today; on 300 labeled emails the system misroutes under 5%.
  4. Explain the safeguards: it answers from the company's documents, it's allowed to say "I don't know", a person reviews high-stakes outputs, and weekly spot checks watch for drift.
  5. Offer the decision: where the VP wants a human in the loop, and what error rate is acceptable for each use.

Answers that fail:

  • Explaining transformers, tokens or sampling to a VP.
  • Promising accuracy will reach 100% with a bigger model or more tuning.
  • Giving no baseline, so "95%" means nothing to the listener.
Q5

Design an end-to-end batching system for LLM queries.

OpenAI · Forward Deployed Engineer · system design

Reported Prep-site guide citing candidates: Exponent ↗. Secondary source; not an official question.

What it probes: Whether you connect latency tolerance to cost, and handle the unglamorous parts: ids, partial failures, retries, rate limits and monitoring.

  1. Clarify: volume per day, how long results can wait, prompt size, output size, and who consumes the results.
  2. Separate interactive from deferrable work. Anything that can wait up to a day goes through the provider batch APIs at 50% off: the $55.00 a month Haiku triage example becomes $27.50.
  3. Pipeline: requests land in a queue or table with a stable id each; a job groups them into batches within the provider's size and token limits, submits, and polls for completion.
  4. Results are matched back by id, validated (parse the JSON, run the checks), and stored with usage and cost; failed or unparseable items are retried a limited number of times, then sent to a dead-letter table for review.
  5. Make it idempotent: re-running a batch must not create duplicates or double-bill. Keep prices and model names in config with a checked-on date.
  6. Stack savings: put the shared instructions first so they can be cached, keep outputs short, and pick the smallest model that passes your evals.
  7. Monitoring: backlog size, batch age, failure rate, cost per 1,000 requests, and alerts when a batch misses its deadline.

Answers that fail:

  • Designing only the happy path, with no ids, retries or partial failures.
  • Sending everything through the real-time API with a big concurrency limit, ignoring the 50% discount.
  • Not asking how long results are allowed to take.

Q7

How do you handle prompt injection in a customer-facing agent?

Several companies (not named) · Forward Deployed Engineer · security

Aggregated Public question list in a prep guide, no company named: Exponent FDE guide ↗. Secondary source. Week 8 goes deeper on injection attacks and defenses.

What it probes: Whether you know prompts alone can't stop injection and design the system so an injected instruction can do little harm.

  1. Define it briefly: text inside the data (an email, a web page, a document, a tool result) that the model follows as an instruction. Indirect injection is the dangerous kind for agents.
  2. Start with the architecture: map what the agent can read and do, and break the lethal trifecta. Don't combine private data, untrusted content and a way to send data out.
  3. Least privilege: only the tools the task needs, read-only where possible, allow-lists for destinations, and human approval for anything irreversible or outbound.
  4. Prompt-level measures as a layer, not the defense: separate instructions from data with tags, and say that text inside the data isn't instructions.
  5. Test it: injection cases in every input channel in your eval set, with checks that the task still gets done (not only that a bad word is absent); log and alert on blocked actions.
  6. Use the security team's language: OWASP LLM01, and a clear statement of residual risk.

Answers that fail:

  • "A strong system prompt tells the model to ignore injected instructions."
  • Relying on a keyword filter for "ignore previous instructions".
  • Treating it as solved by picking a particular model.
